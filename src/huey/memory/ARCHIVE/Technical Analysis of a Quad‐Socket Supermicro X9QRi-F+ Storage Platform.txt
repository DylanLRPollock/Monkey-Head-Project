Technical Analysis of a Quad‐Socket Supermicro
X9QRi-F+ Storage Platform
1. Motherboard Overview: C602 Chipset and Quad-CPU Architecture
The Supermicro X9QRi-F+ is a quad-socket server motherboard built on the Intel C602 chipset, supporting
four LGA 2011 (“Socket R”) CPU sockets
. It is designed for Intel Xeon E5-4600 series processors (both the
original v1 and Ivy Bridge-EP v2 generations) with up to 12 cores per CPU
. The C602 chipset provides
traditional  server  platform  features  such  as  multiple  SATA  ports,  PCI  Express  lane  management,  and
enterprise reliability features (Intel RSTe RAID, AMT/ME manageability, etc.). In a four-CPU configuration, the
processors communicate via Intel’s QuickPath Interconnect (QPI) links, forming a coherent Non-Uniform
Memory Access (NUMA) system. Each Xeon E5-4600 v2 CPU has two QPI links (8.0 GT/s each) to connect
with its neighbors
. The board’s architecture uses a glueless quad-CPU interconnect: the CPUs are
arranged such that each CPU is directly connected to two others via QPI, creating a mesh/ring topology
(one intermediate hop to reach the fourth node). This ensures reasonably low-latency communication
between  processors  for  memory  access  and  cache  coherency,  albeit  with  some  NUMA  effects  when
accessing remote memory (discussed in Section 3). The Intel C602 PCH (Platform Controller Hub) itself
interfaces with one of the CPUs (typically CPU1) via a DMI 2.0 link (essentially a PCIe x4 connection) to
handle peripheral I/O
. This means that onboard devices (SATA ports, etc.) are “owned” by a specific CPU;
in fact, the X9QRi-F+ manual notes that certain features (like the onboard NICs) won’t function unless the
CPU  socket  linked  to  them  is  populated
.  In  summary,  the  X9QRi-F+  provides  a  robust  quad-CPU
infrastructure: Intel C602 chipset, four LGA2011 sockets, and a high-speed QPI network linking the CPUs
for cache-coherent memory sharing
.
Supported CPUs: The board supports the entire Intel Xeon E5-4600 family for 4-socket servers, including
both v1 (Sandy Bridge-EP, up to 8 cores) and v2 (Ivy Bridge-EP, up to 12 cores) models
. A BIOS update
(v3.0 or later) is required to use the Ivy Bridge-EP v2 processors (launched in 2014)
. With an
appropriate BIOS, one can install top-end chips like the Xeon E5-4657L v2 (12 cores @2.4 GHz) or E5-4650 v2
(10 cores @2.4 GHz), which were among the highest-performance options for this platform
. The board is
proprietary EATX in form factor (approximately 16.4″ × 16.8″), meaning it’s larger than standard EATX and
requires a roomy chassis
. Supermicro offered compatible chassis (e.g. 4U models with high-wattage
PSUs, see Section 7) to accommodate this large board and its four CPUs. Key integrated components on the
motherboard  include  an  on-board  Baseboard  Management  Controller  (BMC)  for  IPMI  2.0  remote
management and a basic VGA controller (Nuvoton WPCM450 with Matrox G200 core) for console video
. The board’s dual Intel i350 Gigabit NICs and IPMI module are also noteworthy and will be detailed in
Section 6.
Overall, the X9QRi-F+ provides the foundation for a high-end quad-CPU server, with a layout and feature
set optimized for heavy multi-threaded workloads and large memory capacity. Its chipset and architecture
allow the four CPUs to function as a cohesive system suitable for enterprise tasks. In the context of a
storage hub, the board’s ability to host many cores, large RAM, and multiple high-bandwidth I/O cards (PCIe
slots) is a major asset – albeit one must design around the NUMA nature and I/O attachment specifics (for

2. Processor Specifications: Intel Xeon E5-4600 v2 (E5-4650 v2 /
E5-4657L v2)
The X9QRi-F+ can house up to four Xeon E5-4600 v2 processors, which are Ivy Bridge-EP architecture CPUs
built on 22 nm process (launched Q1’2014)
. For a high-performance configuration, we consider the
top models in this family: for example, the  Intel Xeon E5-4650 v2 (10 cores, 20 threads) and the  Xeon
E5-4657L v2 (12 cores, 24 threads). Each CPU runs at a base frequency of 2.40 GHz, with turbo boost up to
~2.9 GHz on single cores
. These chips feature large last-level caches (25 MB L3 on the 10-core
E5-4650 v2, and 30 MB L3 on the 12-core E5-4657L v2) to accelerate memory access across their cores
. Each core also has a dedicated 64 KB L1 (32 KB instruction + 32 KB data) and 256 KB L2 cache, totaling
640 KB L1 and 2.5 MB L2 per processor for the 10-core model
. The “L” variant (4657L v2) offers more
cores but is optimized for lower voltage; it carries a slightly higher TDP of 115 W, whereas the 4650 v2 is
rated at 95 W TDP
. In a fully loaded system with four CPUs, the aggregate thermal design power is
~380–460 W just for the processors, which has implications for power and cooling (see Section 7).
Microarchitecture and Features: As Ivy Bridge-EP chips, the E5-4600 v2 family brings ISA enhancements
and server-oriented features: they support  Intel 64 (x86-64), Hyper-Threading (2 threads per core), and
Turbo Boost 2.0
. They also include Intel AVX (256-bit vector instructions) and AES-NI acceleration for
cryptography
. Notably, these CPUs are designed exclusively for 4-socket operation (“Scalability: 4S
Only”)
 – they have the necessary QPI links (2 links each) to connect into a quad-processor topology. The
QuickPath Interconnect runs at  8.0 GT/s on these models, providing high bandwidth between CPUs for
memory access and cache coherence
. In terms of memory interface, each E5-4600 v2 has a four-
channel DDR3 memory controller (integrated on the CPU), supporting speeds up to DDR3-1866 (in ideal
configurations)
. At maximum rated speed and with four channels populated, a single CPU can
achieve roughly 60 GB/s of memory bandwidth
. However, note that maximum memory speed might
be reduced in multi-DIMM configurations (e.g., with two DIMMs per channel the speed typically falls to
DDR3-1600 or 1333 – see Section 3).
NUMA and Multi-Processor Implications: With four E5-4600 v2 CPUs, the system is divided into 4 NUMA
nodes (each CPU and its local memory is one node). Memory access is fastest when a core accesses the
memory attached to its own socket, taking advantage of the ~60 GB/s local bandwidth
. Accessing
memory attached to another CPU involves traversing one or two QPI links (with each QPI link providing up
to ~8 GT/s, roughly 32 GB/s half-duplex). This adds latency and slightly reduces bandwidth available to
remote memory. In practice, this means a Linux OS will identify 4 NUMA nodes and can schedule workloads
accordingly. For optimal performance, memory-intensive processes should be “NUMA-aware” – e.g. Linux
can use NUMA balancing or one can pin certain tasks to CPUs and allocate memory on the same node. The
cache coherence between the processors is maintained via a MESIF protocol over QPI; the large L3 caches
on each CPU help reduce the need for remote memory fetches by caching shared data. Still, workloads that
heavily involve cross-CPU communication may see higher latency due to inter-socket links. For a storage
server, this NUMA effect might surface if (for instance) an I/O device on one CPU is being used by a process
running on a different CPU, causing data to hop over QPI. Administrators can mitigate this by aligning
interrupt handling and processes to the CPU that “owns” the storage controller, or by enabling NUMA I/O
optimizations in the OS.

Power and Thermal Profile: The TDP per chip (95–115 W as noted) implies that four CPUs can consume
~400 W at full load. These Xeons use Intel’s power management features (SpeedStep, idle states, power
throttling) to reduce consumption when idle
, but under load they will draw significant power and
generate substantial heat. Each CPU’s maximum case temperature (T_case) is around 75°C
, so adequate
cooling is required to maintain safe operation – typically active heatsinks with high airflow in a server
chassis (Section 7 covers cooling considerations). In exchange for this power usage, the four E5-4650 v2
processors collectively offer 40 physical cores / 80 threads (or up to 48 cores/96 threads with the 12-core
models) and enormous compute throughput for parallel tasks. For perspective, a single E5-4650 v2 delivers
around 2.4 GHz × 10 cores × 8 FLOPs per cycle (with AVX) in peak theoretical performance – on the order of
~192 GFLOPS for double precision, per CPU. Four such CPUs could exceed 0.75 TFLOPS of FP64 theoretical
throughput. While raw FLOPS aren’t typically the limiting factor for a storage hub, this illustrates that the
platform  has  ample  CPU  muscle  for  auxiliary  tasks  like  compression,  encryption  (with  AES-NI),
deduplication, or serving many clients concurrently.
In summary, the Xeon E5-4600 v2 processors used in the X9QRi-F+ bring high core counts, large caches,
and advanced server features (VT-x/VT-d virtualization, AES-NI security, etc.  
) to support enterprise
workloads.  Their  multi-socket  capability  and  memory  bandwidth  make  them  well-suited  to  a  high-
performance storage server that might handle not just disk I/O, but also processing of data (e.g. RAID parity
calculations, ZFS checksums, or application workloads running on the same server). The trade-off is the
high  power  consumption  and  heat,  as  well  as  being  a  generation  behind  modern  CPUs  in  per-core
performance. We will revisit how these CPUs compare to newer platforms in Section 10.
3. Memory Configuration: 82 GB DDR3 ECC across Four NUMA Nodes
Memory Architecture: The X9QRi-F+ has an impressive 32 DIMM slots spread across the four CPU sockets
. Each CPU socket connects to 8 DIMM slots (since each Xeon E5-4600 has a 4-channel memory
controller and the board supports 2 DIMMs per channel). This yields a theoretical maximum of 1 TB DDR3
memory using 32 GB LR-DIMMs in all slots
. In practice, our configuration has a total of 82 GB DDR3
ECC RAM installed. This unusual capacity suggests a non-symmetrical or mixed-DIMM setup – for example,
one might have a mix of 8 GB and 4 GB modules, or perhaps one socket populated with less memory than
the others. Ideally, for balanced performance, memory should be evenly distributed across the four CPUs. A
typical balanced configuration would populate the same number of DIMMs on each CPU (ensuring each
CPU has equal local memory). An uneven total like 82 GB indicates one or more CPUs have an extra module
(or a higher-capacity module) compared to the others. While the system will still function, such imbalance
can lead to NUMA asymmetry (one node has more memory) and potentially some performance variations if
that memory is heavily used. Generally, one would strive to populate either 80 GB (e.g. 4 × 8 GB on each
CPU = 32 GB per CPU, total 128 GB) or 84 GB (e.g. mixing to get 21 GB per CPU) rather than 82; however,
assuming 82 GB is what’s available, the memory controller will interleave memory access in each CPU’s
channels for those installed DIMMs.
DIMM Layout and ECC: Each memory slot on the X9QRi-F+ accepts DDR3 registered ECC memory (RDIMM),
and the board also supports load-reduced DIMMs (LRDIMM) and even unbuffered ECC (UDIMM) in smaller
sizes
. Supported module sizes range from 1 GB up to 32 GB
. In enterprise servers, ECC (Error-
Correcting Code) memory is crucial for reliability: the memory system can detect and correct single-bit
errors and detect (but not correct) double-bit errors
. This significantly reduces the risk of memory
corruption causing data integrity issues or crashes, which is important for a storage hub handling critical
data. The installed 82 GB is ECC-enabled, meaning any single-bit memory error will be transparently fixed

Memory Speed and Bandwidth: The official memory speed support goes up to DDR3-1866 MT/s on this

. However, achieving 1866 MT/s typically requires a limited configuration

two DIMMs per channel are populated, the maximum speed often drops to 1600 MT/s
. In fact, an STH
forum note for this board indicates that “you can't run at 1866 MHz with multiple DIMMs per channel… memory
will be clocked at no more than 1600 MHz”
. Therefore, with 32 slots likely having at least 1 DIMM per
channel (and possibly 2 in some channels), the realistic memory clock is 1600 MHz. At DDR3-1600, each
channel provides ~12.8 GB/s of bandwidth, so each CPU maxes out around  51.2 GB/s of local memory
bandwidth (which aligns with Intel’s numbers for 1600 MT/s operation)
. If the configuration had been
1866, each CPU could reach ~59.7 GB/s
, but again that’s for a light DIMM load. The total system memory
bandwidth (all four CPUs combined) could be on the order of 200 GB/s in theory, but in practice memory
traffic does not perfectly scale that way due to NUMA locality and the fact that each CPU mostly handles its
own memory accesses.
In our 82 GB setup, it’s likely that some channels are not fully populated. For example, one possible
distribution might be: CPU1 has 20 GB (two 8 GB + one 4 GB), CPU2 has 20 GB, CPU3 has 20 GB, CPU4 has
22 GB. This would total 82 GB and give roughly balanced 2-channel vs 2-channel population. In such a case,
not all four channels per CPU are used; using fewer channels can actually allow higher speed (if one channel
per CPU was empty, the others might run at 1866). However, losing a channel reduces peak bandwidth on
that CPU. It’s a trade-off: ideally one populates either 4 or 8 DIMMs per CPU for symmetry. Given that 82 is a
non-power-of-two number, we suspect a slightly non-optimal population. Nonetheless, 82 GB is plenty of
RAM for a storage server, allowing for large disk caches and buffers. Linux can utilize the excess memory for
caching filesystem data (buffer cache), which greatly improves read performance for frequently accessed
data.
Multi-Channel and NUMA Behavior: Each CPU’s memory channels operate in parallel (in interleaved mode
by default), meaning if you populate four identical DIMMs on a CPU (one per channel), the memory
controller interleaves addresses across them for higher throughput. If channels are unevenly populated
(say one channel has a smaller DIMM), the interleaving might not be uniform, but the system will still
manage. The NUMA aspect means that the OS will try to allocate memory on the same node as the running
thread when possible (NUMA locality). For a storage hub, one might pin disk I/O threads or filesystems to
specific CPUs that have direct access to the disk controller (for example, if a RAID card is on a slot attached
to CPU2, it’s beneficial if the I/O processing threads run on CPU2 and use CPU2’s memory). Linux’s NUMA
policy can be configured or left to its automatic NUMA balancing.
ECC  and  Reliability: With  ECC  memory,  the  system  is  well-protected  against  memory  bit  flips.  The
combination of ECC RAM and the chipset’s memory scrubbing and monitoring (via ECC sensors) provides
enterprise-grade reliability for long-term data integrity. Servers like this often run memory tests and
scrubbing in the background. If a DIMM starts to show multi-bit errors (which ECC can’t correct), the system
can alert the admin via IPMI (the BMC can report ECC errors). For a storage server tasked with safeguarding
data,  ECC  memory  is  a  must-have;  the  X9QRi-F+  fully  supports  this,  as  indicated  by  both  Intel  and
Supermicro specs
.

In summary, the memory subsystem of the X9QRi-F+ is very robust and scalable. Our configuration of 82 GB,

multi-DIMM channels) and the benefits of ECC. The multi-channel interleaving per CPU and the NUMA

4. Storage Architecture: Onboard SATA (No Native SAS) and RAID
Considerations
The X9QRi-F+’s onboard storage interfaces are provided by the Intel C602 chipset. The board has 6 SATA
ports in total:  2× SATA 3.0 (6 Gbps) ports and  4× SATA 2.0 (3 Gbps) ports
. These correspond to the
C602’s integrated AHCI controller capabilities: typically, C602 (equivalent to Intel X79/SNB-E PCH) offers two
6 Gb/s SATA channels and four 3 Gb/s channels natively
. No SAS controller is integrated on the X9QRi-
F+, meaning it does not have native support for SAS drives or hardware SAS RAID out-of-the-box
. (By
contrast, a sibling model X9QR7-TF+ included an LSI SAS controller on board, but the X9QRi-F+ omits this,
focusing on SATA only.) Therefore, the storage design for this system must either rely on these 6 SATA ports
or utilize add-in cards for more advanced storage needs.
SATA 3.0 vs SATA 2.0: The two SATA 3.0 (6 Gb/s) ports allow full-speed use of modern SSDs and high-
performance HDDs. Each SATA 3 port has a theoretical max bandwidth of ~600 MB/s, which is ideal for SSDs
that often reach 500+ MB/s sequential throughput. In contrast, the four SATA 2 (3 Gb/s) ports are limited to
~300 MB/s each, which can bottleneck SATA SSDs (which would negotiate to 3 Gb/s and be capped around
~270 MB/s throughput). For spinning hard drives (HDDs), SATA 2 is usually sufficient since most 7.2K RPM
disks deliver 100–200 MB/s, but for SSDs or 15K RPM enterprise drives, the SATA 2 ports would constrain
peak performance. In a mix of SSDs and HDDs, one would typically put the fastest drives (or any SSD scratch
disks, etc.) on the two 6G ports, and use the 3G ports for slower disks or optical drives. It’s noteworthy that
having only 2 SATA 6G ports is a limitation for an intended “storage hub,” since one might easily have more
than 2 SSDs or high-speed drives.
Aggregate Bandwidth and Chipset Limits: All six SATA ports connect through the Intel PCH, which in turn
connects to the CPUs via a DMI link (approximately PCIe 2.0 x4 bandwidth, ~2 GB/s). This bus could become
a bottleneck if multiple SATA ports are active at once. For example, if all 6 ports were simultaneously busy
(say during a RAID rebuild or heavy I/O), the total throughput could, in theory, approach 2×600 + 4×300 =
2,400 MB/s (if two SSDs and four HDDs were all maxed). That is roughly equal to ~19.2 Gb/s, nearing the
DMI’s ~20 Gb/s limit. In practice, you rarely saturate all drives at once with sequential load, but heavy
parallel I/O (like a parity-scan or scrubbing on a multi-disk array) might push the limits. So, the chipset’s own
link to the CPU is something to keep in mind – for extreme storage performance, offloading to PCIe-based
controllers (which can attach directly to CPU PCIe lanes) is often preferable. Additionally, because only one
of the four CPUs is directly connected to the C602 PCH (likely CPU1), any other CPU accessing the SATA
drives must communicate via QPI to CPU1, adding overhead. This again suggests that a storage-heavy
workload should be managed in a NUMA-aware way (e.g., run SATA-based storage services on the CPU
attached to the PCH).

RAID Options (Chipset RAID vs Software vs Hardware): The C602 chipset does offer Intel Rapid Storage
“Enterprise” RAID (RSTe) for the SATA ports, supporting RAID levels 0, 1, 5, 10 in firmware
. In the
specification, this is noted as “RAID 0,1,5,10” for both SATA2 and SATA3 ports
. However, this is essentially
a firmware-assisted software RAID (also known as “fake RAID”) – it requires specific Intel drivers and is
typically  used  on  Windows.  For  a  Linux-based  storage  hub,  one  would  rarely  use  the  motherboard’s
firmware RAID due to limited support; instead, Linux’s own software RAID (MDADM) or a software-defined
storage solution (like ZFS) would be used. Linux MD RAID can easily handle RAID 0/1/5/10 across these
SATA ports, leveraging the CPU for parity calculations in RAID5/6. With four powerful Xeon CPUs, the
overhead of software RAID is not an issue – the system has plenty of processing power for computing parity
or rebuilds. In fact, software RAID may outperform older hardware RAID cards in some cases, because it
isn’t constrained by a fixed XOR engine and can use all available CPU cores for parallel computation
(especially relevant for RAID6 or ZFS’s RAID-Z which involve heavier math like Reed-Solomon or checksums). 
That said, using only the 6 onboard SATA ports limits the number of drives. The user scenario envisions a
“mix of SSDs and HDDs in RAID configurations.” With only 6 ports, one could at most have, say, a RAID-10 of
6 drives or a RAID-5 of 6 drives. 40 TB raw (as mentioned in an example on forums) would be difficult with 6
drives unless using very large disks (e.g., 6×8 TB in RAID-5 gives ~40 TB usable, but that’s pushing it and
rebuild times become worrying with large SATA drives and no hot spares). Indeed, community feedback
suggests “Only 6×SATA is not enough... The OP wants to start with a 40 TB volume in RAID5. That won't work
out  too  well  with  only  6  SATA  ports”
.  The  limitation  is  both  capacity  (number  of  spindles)  and
performance (few spindles mean less aggregate IOPS and throughput). Therefore, a serious storage build
would look to expand storage connectivity via add-on controllers.
Recommended RAID/HBA Add-on Cards: The X9QRi-F+ provides four PCIe slots (see Section 5), which can
be used for storage controllers. For a storage-centric server, a common approach is to add an HBA (Host
Bus Adapter) or a  hardware RAID card to gain more ports (often SAS/SATA ports) and possibly better
performance. Given modern trends, many prefer an HBA with lots of ports (and then do software RAID or
ZFS) rather than hardware RAID cards. A popular choice is an LSI SAS HBA, such as the LSI 9207-8i (which
provides 8 internal SAS/SATA 6G ports on a PCIe 3.0 x8 card). The LSI 9207-8i uses an SAS2308 controller and
can handle 8 drives at full SATA 6G speed without bottlenecking a PCIe 3.0 ×8 slot
. In fact, it’s noted that
“An LSI 9207-8i card is the way to go, it’s PCIe 3.0 x8 and will support 8 drives with ease”, whereas older cards on
PCIe 2.0 ×4 could become a bottleneck
. The 9207-8i or its equivalents (SAS 2308-based HBAs) are widely
recommended as solid choices for building storage arrays
. They support both SAS and SATA drives,
giving flexibility to use enterprise SAS disks or expand beyond the 6 onboard SATA limit. Another similar
card is the LSI 9211-8i (older SAS2008-based, PCIe 2.0 ×8), which also provides 8 ports but on PCIe 2.0 (with
slightly lower aggregate bandwidth). If even more drives are needed, one can use multiple HBAs or a
higher-port  count  HBA  (like  an  LSI  9300-8i  for  SAS3  12   Gbps,  or  16-port  variants).  According  to  a
ServeTheHome guide, the SAS2308 HBAs (e.g., LSI 9207) are still considered “good” options for <8-drive
setups, though newer SAS3 (3008/3108) HBAs offer higher performance for SSD-heavy arrays
. For
mostly HDD usage, the 9207-8i is plenty: it can connect 8 drives and deliver full 6 Gbps to each. With two
such cards, one could have 16 direct-attached drives, which is often more than enough for a storage server
enclosure (and this board has enough PCIe slots to accommodate that).
If one prefers a hardware RAID controller (with on-board cache and XOR engine, etc.), options include LSI/
Avago MegaRAID cards (e.g., LSI 9271-8i for 6G SAS or 9361-8i for 12G SAS). These provide battery-backed
cache and can offload parity calculations. However, using hardware RAID in Linux has pros and cons.
Modern practice, especially with Linux and ZFS, often steers away from hardware RAID in favor of either

Storage Bandwidth Considerations: With a suitable HBA, the system can overcome the DMI bottleneck of
the PCH. For instance, an LSI 9207-8i (PCIe 3.0 ×8) has up to ~8 GB/s bandwidth to the CPU
, which far
exceeds the ~2 GB/s from the onboard SATA. To give a concrete performance example: in one test, eight
SATA SSDs (Crucial M4 drives) connected to an LSI 9207-8i achieved about 4.1 GB/s aggregate throughput
in  sequential  reads
.  This  clearly  broke  the  ~3   GB/s  limit  that  older  PCIe  2.0  controllers  had,
demonstrating the advantage of a PCIe 3.0 HBA for high-bandwidth storage arrays
. In our context,
4.1 GB/s is far above what dual Gigabit LAN can handle – thus if the storage server is to actually serve that
data out, network would be a bottleneck (we’ll address networking in Section 6). But it shows that internally,
the system can move data at multi-GB/s rates if the storage subsystem is designed properly (e.g., using
HBAs and possibly RAID-0 or multiple RAID groups). For HDD arrays, the throughput will be lower (e.g., a
RAID-0 of 8 HDDs might get ~1 GB/s sequential), but still the principle holds: the PCIe-attached controllers
remove chokepoints.
Another aspect is SSD vs HDD mix: If using a mix, one might dedicate SSDs as a cache tier (L2ARC or flash
cache) and HDDs as capacity tier. The absence of NVMe on this older platform means SATA/SAS SSDs are the
go-to for flash storage. One could also use SAS expanders or JBOD enclosures via an HBA external port (if
needed to attach many drives externally). The board, not having onboard SAS, really relies on those
expansions for scaling beyond 6 drives.
Summary of Recommendations: Use the two onboard SATA 6G ports for two of your fastest SSDs (perhaps
for boot drives or a small RAID-1 for the OS, or for caching). Use the four 3G ports for slower disks or not at
all if not needed. For the main storage arrays, add a RAID controller or HBA. A good approach is an HBA
like the LSI 9207-8i (8-port, SAS2 6G) or, if planning lots of SSDs or just to be future-proof, a LSI 9300-8i (8-
port, SAS3 12G) – though on this DDR3 platform, SAS3’s 12 Gbps per port is only fully useful if you have very
fast SSDs or NVMe (which you can’t directly use here). Many homelab and enterprise users have gravitated
to these LSI HBAs; they are known to handle many drives well and have open-source drivers. As one user

For RAID levels: if using Linux MD or ZFS, the CPU can handle RAID5/6 parity calculation across many drives

5. Expansion Capabilities: PCIe Slots for RAID Controllers, NICs, etc.
Despite the large footprint of four CPU sockets and 32 DIMMs, the X9QRi-F+ provides a reasonable set of
expansion slots. It has a total of 4 PCI Express 3.0 slots, arranged as:
2 × PCIe 3.0 x16 slots (full-length, 16-lane slots) 
2 × PCIe 3.0 x8 slots (physical x16 connectors wired with 8 lanes)
.
This layout gives flexibility to install high-bandwidth devices. Typically, in a quad-socket board, the slots are
electrically connected to different CPUs to distribute I/O load. The X9QRi-F+ likely ties each slot’s lanes to a
specific CPU’s PCIe controller. (The exact mapping isn’t in the short spec, but often, CPU1 might feed Slot1
x16 and Slot2 x8, CPU2 feeds Slot3 x16, CPU3 feeds Slot4 x8, etc., or some similar scheme. We do know
from a forum that “socket #4 controls the onboard LAN ports”
, which implies the NIC is on CPU4’s PCIe
lanes; by analogy, some slots could also be attached to particular CPUs.) What this means is that to use all
slots, all four CPUs must be installed. If one or more CPU sockets were empty, some PCIe slots would not
function. In our case, with four CPUs in place, all slots are active and each can operate at PCIe Gen3 speeds
(8 GT/s per lane). 
Bandwidth and Use Cases: The two x16 slots each provide up to ~16 GB/s of bandwidth (in each direction)
at PCIe 3.0. The x8 slots provide ~8 GB/s each. These figures are ideal for high-speed peripherals: - A RAID
or HBA card can be placed in an x8 slot (most such controllers are 8-lane cards) and get full bandwidth. For
instance, an LSI 9207-8i HBA (PCIe 3.0 x8) will saturate an x8 slot and can push those aforementioned 4 GB/
s of data
. - If one uses a high-end RAID card that’s x8 or x16, there’s room. Some RAID cards with more
ports (e.g., 16-port HBA) might use x8 and still be fine. - A 10 Gigabit Ethernet (10GbE) NIC typically uses
PCIe 3.0 x8 (or x4 for single-port). Dual-port 10GbE adapters often are x8. These could be installed to greatly
expand network throughput (since the board only has 1GbE onboard). With two x16 and two x8 slots, one
could conceivably add, for example: one 10GbE (or even 40GbE) NIC, one or two storage controllers, and
still have a slot left for another accessory (like a GPU for compute or an NVMe adapter, etc.). 
Electrical and Physical Considerations: The slots are full-length (x16 physical), which means you can plug
larger cards even into the x8-wired slots. The board being proprietary EATX size means a lot of space; likely,
these slots are arranged spaced out to fit possibly double-width cards (if one wanted to add a GPU or an

Running four high-end Xeon CPUs and a fleet of drives demands careful attention to power and cooling in

9. Performance and Benchmarks: Expected Throughput and Parallel
Processing
When evaluating performance, we should consider two aspects of this system:  storage I/O throughput
(especially in RAID configurations) and compute capability for parallel processing (which could involve
RAID parity calculations, compression, or serving concurrent clients). While specific benchmark results for
exactly this configuration might not be readily available, we can extrapolate from similar setups and known
hardware limits:
Disk I/O Throughput: With a mix of SSDs and HDDs in RAID, the throughput will heavily depend on how
the disks are organized: - If using a RAID-10 of HDDs (say 4 or 6 drives), one might expect sequential read/
write in the range of a few hundred MB/s (perhaps 300–600 MB/s). HDDs in RAID-10 will get some benefit of
striping (maybe ~N/2 times the performance of one disk). 6 fast SATA HDDs could approach ~1 GB/s read (if
each is 180 MB/s, striped across 3 pairs, ~540 MB/s, with some head movement, etc.). Latency for small
random I/O would still be limited by the ~10 ms seek of drives, but multiple drives provide better IOPS
scaling. 6 drives could yield maybe ~600 IOPS instead of 100, if they all seek in parallel (roughly linear with
count for random). - If using SSDs in RAID-0 or RAID-5, throughput can be very high. A single SATA SSD can
do 500–550 MB/s sequential. In a RAID-0 of 4 SSDs, one could see ~2 GB/s. We have the earlier example: 8
SATA SSDs on an LSI 9207 HBA reached ~4.1 GB/s sequential read
. That’s near the max of the PCIe
x8 link. With fewer SSDs, say 4, on a single 6G HBA, we might see ~2–2.2 GB/s (which might saturate a PCIe
2.0 ×8 or stay within PCIe 3.0 ×4). - If using a RAID-5/6 with HDDs, write performance can be the limiting
factor (due to parity overhead and random write penalty). However, this system’s CPU can handle parity calc
well, so it’s more about disk speed. For example, a 5-drive RAID-5 of 7200RPM HDDs might give ~500 MB/s
reads (since 4 data stripes read in parallel), but writes may be lower due to read-modify-write cycles (maybe
half of that, unless doing large sequential writes which can use stripe-aligned full writes). - RAID-5/6 with
SSDs: The CPU can calculate parity at several GB/s (especially with AVX2, though these are AVX1 era, still
fine). The limitation would likely be the SSDs and controller. 4 SSDs in RAID-5 might have writes around the
speed of 3 SSDs (since parity overhead) – e.g. if each is 500 MB/s, maybe 1500 MB/s writes, and reads
around 2000 MB/s. These are ballpark. Such a setup would be entirely bottlenecked by the 1GbE network if
only using onboard NIC, which is why a 10GbE is needed to see these benefits externally.
Networking Throughput: On dual GbE, the max combined output is ~2 Gbps (~250 MB/s). This is easily
achieved even by a single modern HDD or a couple of them in RAID. So a single large file transfer could
saturate one 1Gb link at ~110 MB/s. With multiple transfers, both ports can be used either separately or
bonded. But either way, if the storage array can push GB/s, the network is the choke if left at 1Gb. With
10GbE, you open up to ~1.1 GB/s per link (for reference, a single SATA SSD’s sequential speed is ~0.5 GB/s,
so even one or two SSDs can saturate 10GbE). For truly maxing out a multi-SSD array, multiple 10GbE or a
40GbE would be needed. The system can support that as discussed.
Memory and Cache Effects: With 82 GB RAM, a lot of reads might come from cache if the same data is
accessed repeatedly. Linux will buffer file reads in memory (as page cache). So if, for instance, a set of files
<82 GB is frequently read, after initial load they’ll be served from RAM at basically memory speed. That
could be tens of GB/s internal throughput. But again, externally the network is the limiter. Internally, if there
was a compute job reading data, it could get it from cache quickly. The memory bandwidth per CPU (~50-60
GB/s) means even with multiple threads doing I/O, the NUMA-local memory can supply data fast enough to
not impede disk speeds.

Parallel Processing / CPU Performance: The four Xeon E5-4650 v2 (or 4657L v2) provide a large number of
cores and threads (40 cores / 80 threads in total with 4×10-core + HT). This is beneficial if the storage server
is performing not just simple file serving, but also things like compression, encryption, deduplication, or
hosting VMs/containers. 
For example, if using ZFS, the server could enable compression (LZ4) which these CPUs can handle at
hundreds of MB/s per core. With many cores, ZFS could potentially compress multi-gigabytes per
second of throughput on the fly. Same for checksum calculations (ZFS Fletcher or SHA-256
checksums would be spread across cores).
If doing software RAID-6, the dual parity calculations (like P and Q using Reed-Solomon) would
normally be CPU-intensive, but the mdadm driver uses SIMD optimizations. The presence of AVX
(and potentially the pclmulqdq instruction for carry-less multiply used in some RAID6 algorithms)
means the CPU can accelerate these computations significantly. It’s not unrealistic to see RAID6
parity generation well above 5 GB/s on a modern multi-core – certainly within what these chips can
do collectively. So the CPU won’t be a bottleneck for RAID parity in most scenarios; the drives will
max out first.
IOPS and concurrency: With 40 physical cores, the system can handle many threads doing I/O. For
instance, it could serve dozens of simultaneous clients over NFS/CIFS without pegging the CPU. Each
network interrupt and disk interrupt can be spread over cores (by IRQ affinity or Linux’s multiqueue
block layer). The result is that even under heavy multi-user load, the CPU usage might remain
moderate on each core, using maybe 10-20 cores fully and leaving others for other tasks or spikes.
This is a big advantage over a single or dual-socket system when dealing with large-scale workloads.

available. If network is 10GbE (~1.1 GB/s), it can only send out that much at once. So if 10 clients, each might

Local Processing: If the storage hub is not just a NAS but also runs local compute tasks (like maybe data

Potential Bottlenecks: We should identify what could limit performance in certain cases: -  Network
Bottleneck: As noted, if only using 1GbE, the network is the throughput bottleneck for large transfers. Even
with 10GbE, if the storage is extremely fast (like multiple SSDs), a single 10GbE link may become the new
bottleneck at ~1.1 GB/s. For maximum, multiple 10Gb links or a 40Gb link would be needed to fully not
bottleneck a very high-end all-SSD array. -  Storage Bottleneck: If mostly HDDs are used, random I/O
performance will be the bottleneck (the mechanical latency). The CPUs can queue a lot of I/O, but disks only

more than 3 GB/s of traffic needs to go from one CPU’s memory to another’s NIC, you’d max the QPI. But
that scenario can be avoided with good NUMA strategy (e.g., run the file server daemon on the CPU that
has the NIC and/or place its buffers on that node). -  CPU Bottleneck: If doing something heavy like
software encryption on all traffic (e.g., IPSec or TLS for every file transfer, or using full-disk encryption with
dm-crypt on a multi-gigabit stream), then CPU could become a bottleneck. AES-NI helps a lot though – these
CPUs have AES-NI, which can encrypt at multi-gigabit speeds per core (roughly, AES-128-GCM can do a few
hundred MB/s per core on Ivy Bridge, so with 40 cores, even 10+ GB/s aggregate encryption is possible). So

10. Use-Case Analysis: Quad-Socket Storage Server vs Newer
Platforms
In this section, we evaluate the X9QRi-F+ quad-Xeon system as a dedicated storage server, considering its
advantages and drawbacks in the context of modern alternatives.
Strengths of the X9QRi-F+ Platform as a Storage Hub: - Massive Parallelism: With up to 40 cores / 80
threads, this server can handle a highly concurrent workload. For a storage server, this means it can serve
many clients simultaneously, handle multiple RAID rebuild threads, encryption tasks, or compression tasks
in parallel. Newer single- or dual-socket platforms might have high core counts too (e.g., AMD EPYC can
have 64 cores on one chip), but in the era this was built, 4-socket was the way to get 40+ cores. Even today,
40 cores is substantial for I/O handling. This is advantageous if the storage server doubles as a compute
server (running VMs or heavy file indexing, etc.). - Large Memory Capacity: Supporting up to 1 TB RAM
(and practically using tens or hundreds of GB affordably), it allows huge disk caches and buffers. Our 82 GB
is relatively modest compared to the 1 TB max, but still, 82 GB is plenty for caching a lot of filesystem data.
Many modern NAS appliances skimp on RAM (perhaps 16–32 GB in smaller units), whereas here we can
cache aggressively, reducing disk reads and improving performance for repeated access patterns. Also, the
ECC RAM ensures reliability for cached data. -  High I/O Expandability: The four PCIe 3.0 slots give it
flexibility to integrate new technologies. We can add 10GbE or even 40GbE NICs to upgrade network
bandwidth – something mandatory to fully utilize a fast disk subsystem. We can also add the latest storage
controllers or even NVMe drives via adapters. While the board itself is from 2013 era, it can accommodate,
for example, a 2019 NVMe SSD in a PCIe slot (though at PCIe 3.0 speeds). This extendability means the
system can be upgraded to keep pace with certain advancements (to a point). -  Proven Reliability and
Support: Enterprise boards like this have validated designs and often long-term support (BIOS updates,
etc., though by 2025 it’s EOL, but during its prime it had support). The use of server-grade components
(Intel NIC, IPMI, ECC memory) and form factor means it’s built for 24/7 operation. For a storage server
where uptime and data integrity are paramount, this is important. Many “newer” platforms like modern
consumer boards with lots of SATA might not have IPMI or ECC, which are big pluses for reliability and
remote management. - Cost Efficiency (used market): Although not an “in-technical-spec” advantage, by
2025 this platform can be obtained relatively inexpensively on the secondary market, while still delivering
very  solid  performance.  The  ServeTheHome  forum  notes  that  4×  E5-4650  v2  CPUs  can  be  found  for
relatively low cost now
. This means you can build a powerful storage server for a fraction of the cost of a
brand-new enterprise server. For a certain audience (like homelabs or budget-conscious enterprises), this is
a practical advantage.

Advantages over Newer Platforms: It might seem counter-intuitive that an older platform has advantages
over newer ones, but there are a few scenarios: - Memory and I/O Bandwidth vs cost: Many newer single-
socket solutions (like Xeon Scalable Silver/Gold or AMD EPYC) offer huge performance, but the platforms
and  memory  (DDR4/DDR5)  are  expensive.  The  X9QRi-F+  can  use  cheaper  DDR3  ECC  modules  readily
available used
. If one needs a very large memory pool (hundreds of GB) for a storage server (for
caching or in-memory datasets), populating this board might be cheaper than buying high-capacity DDR4/
DDR5 for a new system. And its aggregate memory bandwidth (4 CPUs × 4 channels each) is still quite high
(theoretically ~200 GB/s) – a single newer CPU might have 8 channels at faster DDR4, but e.g. 8×25.6 GB/s =
~204 GB/s, so not far off. - PCIe Slots Count: Some modern single-socket boards (e.g., ATX boards) might
have fewer PCIe slots (maybe 3 or 4 total, often with lane bifurcation for M.2). The X9QRi-F+ gives 4 full slots
without needing to share lanes with M.2 devices etc. A modern dual-socket might equal or exceed that, but
single-socket mainstream could be limited. For example, if comparing to a Xeon D appliance or a smaller
server board, those often have limited expansion. - NUMA segregation for performance isolation: With 4
CPUs, one could dedicate certain tasks to specific CPUs. For example, you could run a database server on
CPU3 with its local memory, and the file server on CPU1, somewhat isolating their memory and CPU usage
(they communicate via QPI if needed but can largely work separately). On a single-socket multi-core, all
tasks share the same memory controller and caches, which is usually fine but in heavy multitasking, NUMA
isolation can sometimes help performance tuning.
However, there are notable disadvantages and bottlenecks as well, especially compared to state-of-the-
art: - Power Efficiency: Newer platforms (like 2nd Gen Xeon Scalable or AMD EPYC) deliver much better
performance per watt. A single EPYC 7302 (16-core) might equal or beat two of these old 10-core Xeons in
many workloads while consuming far less power. The X9QRi-F+ with four CPUs will draw significantly more
power at idle and load. This affects operating cost (electricity, cooling requirements) and makes the system
less “green.” If this is an always-on storage server, over years the power bill difference might justify a newer
more efficient system. - Heat and Noise: As discussed, this system requires strong cooling. Modern CPUs
are also hot, but you might have half as many in a simpler configuration. A new system with a single 32-core
CPU might be easier to cool (and quieter) than four 10-core ones. If the storage server is in a non-
datacenter environment, noise could be an issue. The X9 will be loud when fans ramp up. - Performance
per Core: Each Ivy Bridge core at 2.4 GHz is much slower in single-thread than a modern core at 3+ GHz
with IPC improvements. Some storage tasks (like serving a single threaded request, or running a mostly
single-threaded app) would be faster on a new CPU. If the workload cannot utilize many cores, the newer
platform is preferable. For instance, metadata operations in a filesystem (like directory listings) often run
single-threaded per request. A faster core would respond quicker. However, if many users do that, the old
platform can handle concurrency, but any one operation might be slower than on a new CPU. - Missing
Modern Features: Newer platforms have PCIe 4.0 or 5.0 (higher bandwidth for HBAs and NICs), NVMe U.2
or M.2 slots on board, built-in 10GbE on many server boards, and support for faster memory (DDR4/DDR5)
which can help in some edge cases. The X9QRi-F+ is limited to PCIe 3.0 and no native NVMe. So high-end
NVMe SSDs will be capped at ~3.3 GB/s on PCIe 3.0 x4. Also, things like NVMe-oF (NVMe over Fabrics) target
mode likely run better on newer gear with dedicated NVMe slots and faster networking. If one wanted to,
say, directly attach NVMe drives or use GPUs (for some reason in a storage/AI combo server), a new
platform with PCIe4/5 would greatly outperform. - Support & Lifecycle: By 2025, this platform is long out of
official support (EOL). Firmware updates (BIOS, BMC) are no longer released. Newer OS features might not
be validated on it. In contrast, a new platform would have ongoing updates and security fixes (e.g., new
mitigations for side-channel attacks might not be back-ported to older microcode here). That might be a
consideration for enterprise use (security). - Density: A modern single-socket 1U could potentially replace a
larger 4U older system in terms of performance, while consuming less space and power. If datacenter rack

Potential Bottlenecks Recap: - Network Bottleneck: On our platform specifically, if it’s not upgraded, the
dual 1GbE is a bottleneck. But we assume we can upgrade via PCIe (which is an extra cost/complexity
compared to newer boards that might have 10G built-in). - Single-thread bottlenecks: As noted, any single
client’s performance (latency or single-stream bandwidth) might be limited by one core’s performance or
one link’s capacity. Newer tech could have higher per-thread performance and features like RDMA (Remote
Direct  Memory  Access  with  modern  NICs,  though  one  can  add  RDMA  NIC  here  too).  -  Cross-CPU
bottlenecks (NUMA): If not carefully managed, memory access across QPI could become a bottleneck for
some workflows. For example, if a RAID card on CPU2 is frequently accessed by a process running on CPU1,
the QPI latency will add. In a newer single-socket, no NUMA, so simpler. However, OS can mitigate with
NUMA pinning or one can ensure the major services are local to their I/O. This is just a complexity factor
that doesn't exist on single-socket systems.
Ideal Use Case for X9QRi-F+: It shines in a scenario where you need a large amount of resources thrown at
a problem without high incremental cost: - As a dedicated storage server, especially if you combine roles
(maybe it’s also doing processing on the data). For example, a Hadoop or distributed storage node with
compute, where having 4 CPUs can do storage management and run data tasks. - As a virtualization host
with a lot of local storage (the cores can host many VMs/containers and the drives give large storage pool).
Though storage in virtualization nowadays often uses centralized storage, for smaller setups this could be
an all-in-one. - If you specifically need lots of PCIe devices (maybe multiple HBAs connecting to lots of JBOD
enclosures, plus multiple NICs), the quad-socket can handle that addressing and interrupts across CPUs
nicely.
Compared to a New 2025 platform (for example, a single-socket AMD EPYC 7552 with 48 cores, PCIe4,
etc.): - The new one would have higher memory bandwidth (8-ch DDR4 or DDR5), much higher per-core
speed, more PCIe lanes (128 lanes PCIe4), and integrated features, all in a simpler package. It would likely
outperform the old one in almost every metric while using less power, except possibly raw memory capacity
if the new one didn’t have as many DIMM slots (though many new boards support 16 DIMMs per socket,
which with 64GB modules is already 1TB, so moot). - The trade-off is cost: that EPYC board + CPU might cost
a lot more than repurposing an existing X9 server. - So one could say: the X9QRi-F+ is “advantages over newer
platforms” mainly in cost for performance (on second-hand market) and the ability to reuse existing
DDR3 memory and older enterprise parts. It also runs legacy OS easily (if someone needed to run an
older OS for compatibility, though for a new deployment one would use a current OS).
Potential Bottlenecks Already Identified: network, storage interface, single-thread, power/cooling. We
should ensure we articulate them: - Network: limited onboard to 1GbE (need upgrade). - DMI: limits
onboard SATA aggregate (~2GB/s). - QPI: remote memory/disk access overhead, as described. - Possibly the
generation’s lack of certain acceleration (no NVMe, no PCIe4, etc., which we've covered). - Disk count: only 6
onboard without HBA (again solved by expansions).
Long-term considerations: Another soft point: as technology moves, newer NVMe drives or such might
saturate PCIe3 quickly. If down the road one wanted to attach NVMe U.2 SSDs (via an HBA like Broadcom
9400 series or similar), each NVMe can do 3-4 GB/s, and a PCIe3 x8 HBA might handle maybe 2 of those at
full speed. Newer boards with PCIe4 could handle twice as much per slot. So for extremely high-end all-

Conclusion on use-case: As a dedicated storage server, the X9QRi-F+ is very capable – it offers enterprise
reliability  (ECC,  IPMI),  high  concurrency,  and  flexibility  to  attach  lots  of  drives  and  networks.  It  can
absolutely function as a central storage hub for a lab or a data center tier (like a backup server or secondary
storage node). Its advantages are more prominent if one already has the hardware or can get it cheaply,
and if the power usage is not a major concern. Against newer platforms, it’s largely outclassed in efficiency
and  simplicity  (newer  one  might  do  the  same  job  with  fewer  CPUs),  but  not  necessarily  in  raw  I/O
performance if both are equipped similarly. With proper tuning, a quad E5-v2 system can still saturate
modern storage devices and network links to deliver high throughput. 
Bottlenecks to monitor include: - Network – likely the first limiting factor; solve by adding 10GbE. - Disk I/
O – ensure use of HBAs to avoid the SATA port bottleneck. - NUMA alignment – avoid cross-node penalties
by configuring services appropriately. - Power/Cooling – make sure the environment supports it, otherwise
thermal throttling or component strain could become an issue (which is a “bottleneck” in a sense).
Finally, one might consider the maintenance: with more components (4 CPUs, 32 DIMMs), there’s a larger
surface for potential failure (like more DIMMs that could go bad, etc.) compared to a simpler system. But
that’s mitigated by good hardware (ECC catches memory errors, etc.) and possibly by having spares if
needed.
In summary, the X9QRi-F+ is  “overkill” in some ways for a storage server but that overkill translates to
headroom and robustness. It’s an older tank of a server board that, when outfitted correctly, can still deliver
enterprise-level storage performance. However, the user should be aware of its hunger for power and
cooling, and the need to augment it with modern interconnects (like 10GbE) to truly leverage its capabilities
in a present-day network.
