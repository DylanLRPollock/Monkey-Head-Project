## 1. Background: The Commodore 64 Keyboard Design and Protocol

### 1.1 Keyboard Matrix Architecture

The C64 keyboard is a classic **8×8 matrix** of switch contacts, yielding **64 matrix positions** corresponding to 64 of the 66 physical keys. Each key connects one of 8 "column" lines to one of 8 "row" lines. The matrix reduces wiring from 66 individual wires to 16 lines (8 rows + 8 columns).

**Verification:** The C64-Wiki confirms the matrix directly covers 64 out of the 66 keys. The remaining two are **Restore** (tied to the NMI line, not part of the matrix) and **Shift Lock** (tied to the same wire as LSHIFT).

### 1.2 Special Keys — Shift Lock and Restore

| Key | Behavior | Circuit |
|-----|----------|---------|
| **Shift Lock** | Latching switch, mechanically holds left Shift down | Wired in parallel with left Shift switch |
| **Restore** | Non-maskable interrupt (NMI) | Dedicated switch to ground on NMI line |

For conversion, Restore can be treated as a separate button (e.g., mapped to a modern key or special function) by reading its state on a GPIO input.

### 1.3 Original Scanning Mechanism

The C64's keyboard matrix is scanned by **CIA#1**. Port A (PA0–PA7) connects to column lines, and Port B (PB0–PB7) connects to row lines. The KERNAL routine drives one column at a time (writing a byte to $DC00 with a single 0 bit) and reads back from $DC01 to see which row bits are 0. The ROM scanning routine cycles through all 8 columns thousands of times per second. No interrupt is generated by keys—the process is purely polled in firmware.

**Verification:** The C64 keyboard is a passive switch network with no electronics or encoding logic of its own. All keys (except Restore) are read via matrix scanning.

### 1.4 Keyboard Connector Pinout

The C64 keyboard has a **single-row 20-pin connector** (0.1" pitch):

| Connector Pin | Function |
|---------------|----------|
| 1 | GND |
| 2 | NC (orientation key) |
| 3 | Restore |
| 4 | +5V (not used by keyboard PCB) |
| 5–20 | 16 matrix lines |

**Verified Pin Mapping (from Proton-64 project):**

| Connector Pin | Matrix Line | Connector Pin | Matrix Line |

| 5 | C3 | 13 | R0 |

| 8 | C4 | 16 | R4 |

| 10 | C2 | 18 | R2 |
| 11 | C1 | 19 | R1 |
| 12 | C0 | 20 | R7 |

## 2. Objectives and Benefits of Repurposing the C64 Keyboard

### 2.1 Giving New Life to Vintage Hardware

Converting a C64 keyboard into a USB HID allows enthusiasts to reuse authentic retro hardware as a modern input device. This offers a unique typing experience and preserves computing history. It is especially appealing for retro-computing fans running C64 emulators (VICE, BMC64).

### 2.2 Technical and Educational Value

This project is a valuable exercise in embedded system design and interfacing, touching on GPIO usage, matrix scanning, keyboard protocols, and USB HID implementation.

### 2.3 Cost and Simplicity

The C64 keyboard connects directly to the Pi's GPIO header without need for intermediate microcontrollers or active converters. This keeps hardware simple and low-cost. Commercial products like the **Keyrah** interface board exist, but the Pi approach avoids extra hardware.

## 3. Hardware Design: Custom Interface Board and GPIO Wiring

### 3.1 Overview

A custom interface board serves three purposes:
1. Adapt the C64's 20-pin keyboard connector to the Pi's 40-pin GPIO header
2. Provide stable power connections (5V and ground)
3. Facilitate USB output from the Pi to the host computer

### 3.2 GPIO Configuration and Levels

The Raspberry Pi's GPIO operates at **3.3V logic**. This is sufficient for the C64 keyboard matrix, which consists of passive switches to ground. **No level shifting is required**—3.3V on the Pi's outputs and pull-ups works fine to detect key closures.

| GPIO Mode | Configuration |
|-----------|---------------|
| **Columns** | Outputs (driven low one at a time) |
| **Rows** | Inputs with pull-ups (internal ~50 kΩ) |
| **Restore** | Input with pull-up |

### 3.3 Physical Board and Ports

A prototyping PCB can be used with a dual-row 40-pin female header for the Pi and a single-row 20-pin header for the C64 keyboard connector. The board also accommodates:
- Micro-USB or USB-C jack for host connection (Pi Zero OTG)
- DC barrel jack or micro-USB for 5V power input

**Verification:** The BMC64 project demonstrates this exact approach, using a Raspberry Pi 3B+ connected to the keyboard via GPIO.

### 3.4 Electrical Considerations

| Consideration | Detail |
|---------------|--------|
| **Pull-ups** | Pi's internal pull-ups (weak, ~50 kΩ) sufficient for row lines |
| **Series Resistors** | Optional ~220 Ω on matrix lines for short-circuit protection |
| **Ground** | Common ground between keyboard, Pi, and host PC |
| **ESD Protection** | TVS diodes or series resistors recommended |
| **Power** | Keyboard itself has no active power draw |

## 5. Software Implementation: Matrix Scanning and USB HID Emulation

### 5.1 GPIO Initialization

```python
import RPi.GPIO as GPIO
GPIO.setmode(GPIO.BCM)

col_pins = [4,17,27,22,5,6,13,19]  # Example GPIO numbers
row_pins = [26,16,20,21,18,23,24,25] # Example GPIO numbers

# Rows as inputs with pull-ups
for rp in row_pins:
    GPIO.setup(rp, GPIO.IN, pull_up_down=GPIO.PUD_UP)

# Columns as inputs (high-Z) initially
for cp in col_pins:
    GPIO.setup(cp, GPIO.IN, pull_up_down=GPIO.PUD_OFF)
```

### 5.2 Virtual HID Device Setup

```python
from evdev import UInput, ecodes as e

ui = UInput(name="C64 Keyboard", vendor=0x1234, product=0x0001)
```

**Verification:** The `evdev` library supports creating virtual input devices via `UInput`. The `evdev` module provides Python bindings to the Linux input subsystem.

### 5.3 Matrix Scanning Loop

```python
pressed_set = set()
SCAN_INTERVAL = 1/60  # 60 Hz

while True:
    syn_needed = False
    for i, col_pin in enumerate(col_pins):
        # Drive column i low
        GPIO.setup(col_pin, GPIO.OUT, initial=GPIO.LOW)
        
        for j, row_pin in enumerate(row_pins):
            idx = i*8 + j
            if GPIO.input(row_pin) == GPIO.LOW:
                if idx not in pressed_set:
                    pressed_set.add(idx)
                    ui.write(e.EV_KEY, keymap[idx], 1)
                    syn_needed = True
            else:
                if idx in pressed_set:
                    pressed_set.remove(idx)
                    ui.write(e.EV_KEY, keymap[idx], 0)
                    syn_needed = True
        
        # Release column (back to high-Z)
        GPIO.setup(col_pin, GPIO.IN, pull_up_down=GPIO.PUD_OFF)
    
    if syn_needed:
        ui.syn()
    time.sleep(SCAN_INTERVAL)
```

**Verification:** A similar structure is used in the `rpi-gpio-matrix-keyboard` project, which runs at 60 Hz and uses a Python `evdev`-based prototype (taking ~6% CPU).

### 5.4 USB HID Output

The Raspberry Pi, when configured properly, appears as a USB keyboard to any host. Each scan cycle, `ui.syn()` emits buffered key events. The uinput system handles combining these into USB HID reports.

**USB Gadget Configuration (Pi Zero):**

## 6. Challenges and Considerations

### 6.1 Key Debouncing

Mechanical key switches can bounce, producing rapid on/off fluctuations for a few milliseconds. At 60 Hz scanning (~16.7 ms per scan), very brief bounce is naturally filtered. For professional polish, implement a state machine requiring 2 consecutive LOW reads before accepting a key-down.

### 6.2 Ghosting and Masking

The C64 keyboard **lacks diodes** on each switch, making it vulnerable to ghosting when certain combinations of simultaneous keys are pressed. Ghosting occurs when three keys form a rectangle in the matrix—the fourth corner can erroneously appear "pressed".

**Mitigation Options:**

| Approach | Feasibility | Notes |
|----------|-------------|-------|
| **Software ghost detection** | Partial | Detect and ignore phantom reads |
| **Add diodes** | Requires modification | 1N4148 in series with each column line |
| **Accept limitation** | Practical | Normal typing rarely triggers ghosting |

### 6.3 Latency and Timing

Using a Raspberry Pi running Linux means no hard real-time guarantee. A 60 Hz loop in Python uses only a few percent CPU on the Pi. USB HID keyboards poll at 125 Hz (every 8 ms) by default, which is smooth for typing.

**Verification:** The C version of the `rpi-gpio-matrix-keyboard` driver uses <1% CPU at 60 Hz, while the Python prototype uses ~6%.

### 6.4 Power and Safety

| Consideration | Detail |
|---------------|--------|
| **Power source** | Pi Zero can be powered via host USB (gadget mode) |
| **Backfeeding** | Avoid powering from both host and external supply simultaneously |
| **ESD protection** | Avoid touching connector pins while powered |

### 6.5 Mechanical Fitting

The Raspberry Pi (especially Pi Zero) fits inside the C64 case with room to spare. The custom board should be shaped to mount near the original keyboard cable entry point. Care must be taken not to strain the 35+ year old keyboard connector.

## 7. Comparison with Other Retro-Keyboard Conversion Projects

### 7.1 Microcontroller-Based Converters

| Controller | Firmware | Advantages |
|------------|----------|------------|
| **Arduino Pro Micro (ATmega32u4)** | LUFA/Arduino Keyboard library | Low latency, simple |
| **Raspberry Pi Pico (RP2040)** | QMK (C64P) | $4, PIO, deterministic timing |
| **Teensy** | QMK | High performance |

**Verification:** The C64P project provides QMK-based firmware for the Raspberry Pi Pico to connect an original C64 keyboard via USB.

### 7.2 Commercial Adapters

The **Keyrah** is a well-known product that provides an interface for Commodore 64 keyboards to USB. It requires no programming—plug and play. The Pi approach is DIY and offers more customization.

### 7.3 Feature Comparison

| Feature | Raspberry Pi (Linux) | Microcontroller (QMK) | Keyrah |
|---------|---------------------|----------------------|--------|
| **Programmability** | High (Python/C) | Medium (C firmware) | None |
| **Latency** | Low (~20 ms) | Very low (<5 ms) | Low |
| **Extensibility** | High (can run emulator) | Low | None |
| **Cost** | $10–35 | $4–20 | ~$40 |
| **Boot time** | Seconds | Instant | Instant |
