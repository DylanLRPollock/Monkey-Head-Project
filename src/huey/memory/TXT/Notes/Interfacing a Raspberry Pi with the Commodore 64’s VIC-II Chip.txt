## 1. Introduction and Technical Background

The MOS Technology VIC-II (Video Interface Chip II) is the graphics and video generator used in the Commodore 64 (and C128), released in 1982. Manufactured by MOS Technology, the VIC-II (models 6567/8562 NTSC, 6569/8565 PAL) outputs the C64's video signals and manages video memory accesses. It produces a 320×200 pixel bitmap or character-based display with 16 colors, hardware sprites, smooth scrolling, and raster interrupts.

The VIC-II is a **bus-mastering device** that shares the system bus with the 6510 CPU: it accesses memory during certain half-clock cycles (stealing cycles from the CPU) and performs DRAM refresh duties. This means the VIC-II tightly coordinates with the CPU via signals that halt the CPU when the video chip needs the bus.

### 1.1 VIC-II Key Specifications

| Feature | Description |
|---------|-------------|
| **Video Modes** | 40×25 text; 320×200 hi-res bitmap (16 colors); multicolor (160×200); sprites (8 per line) |
| **Colors** | 16 (palette built-in) |
| **Sprite Hardware** | 8 sprites, 24×21 pixels (or 12×21 in multicolor) |
| **Memory Addressing** | 14-bit address bus (A0–A13), multiplexed for DRAM |
| **Bus Mastering** | Yes – Alternates memory access with CPU (CPU halted on VIC-II access cycles) |
| **Notable Signals** | BA (Bus Available) and AEC (Address Enable Control) to coordinate CPU access; Φ2 clock input; RAS/CAS for DRAM; D0–D7 data bus; analog video outputs (Y/C) |

**Verification (Pinout):** VIC-II pin 13 (Vdd) connects to **+12V DC (6567/69)** or **+5V DC (8562/65)**. Pin 40 (Vcc) is +5V DC. Pin 12 (BA) outputs the READY signal: when going LOW, the CPU waits after next read cycle. Pin 16 (AEC) connects directly to AEC of the CPU: when going LOW, the CPU puts its bus lines into high impedance.

### 1.2 The Raspberry Pi and Its GPIO Interface

The Raspberry Pi is a modern single-board computer with a Broadcom SoC, ARM CPU, and a 40-pin GPIO header. Over two dozen pins can be used as general-purpose I/O.

**Critical Electrical Constraint:** Every GPIO pin on every Raspberry Pi board — Pi 4, Pi 5, and Pico alike — runs at **3.3V logic and is not 5V tolerant**. Directly connecting a 5V output to a Pi's GPIO will damage the Pi.

| Parameter | Raspberry Pi GPIO | C64 Signals |
|-----------|-------------------|-------------|
| **Logic High** | 3.3V | 5V |
| **5V Tolerant?** | **No** | N/A |
| **Input Protection** | None (direct to SoC) | N/A |

The Pi's GPIO can be programmed from user space (e.g., via `RPi.GPIO` or `pigpio` in Python) and can toggle or read pins with microsecond-scale timing under optimal conditions. However, a stock Raspberry Pi runs a full Linux OS which does not guarantee real-time performance, and the CPU time must be shared with the operating system unless bare-metal programming or specialized kernel modules are used.

## 2. Passive Monitoring of VIC-II Signals with a Raspberry Pi

One approach to interfacing the Raspberry Pi with the VIC-II is **passive monitoring**, where the Pi listens in on the VIC-II's signals without disturbing the C64's normal operation.

### 2.1 Key Signals to Monitor

| Signal | Purpose | Direction |
|--------|---------|-----------|
| **A0–A13** | VIC-II memory fetch addresses | VIC → Pi |
| **D0–D7** | Data bus values | Bidirectional (monitor as input) |
| **BA** | Bus Available (goes low when VIC-II uses bus) | VIC → Pi |
| **Φ2** | 1 MHz system clock phase | VIC → Pi |
| **R/W** | Read/Write indicator | CPU → Pi |
| **IRQ** | Interrupt request line | VIC → Pi |
| **AEC** | Address Enable Control | VIC → Pi |

### 2.2 Level Shifting for Passive Monitoring

Passive monitoring requires that the Raspberry Pi's presence does not load or disturb the signals. This is achieved by using high-impedance buffer circuits or dedicated level shifters that sense the 5V signals and output a safe 3.3V logic signal to the Pi.

| Component | Type | Use Case |
|-----------|------|----------|
| **74HC4050** | Hex buffer (unidirectional) | Shifting 5V down to 3.3V (input to Pi) |
| **74HCT245 / 74LVC245** | 8-bit bus transceiver | Bidirectional data bus with direction control |
| **74HC541** | Octal buffer | Address lines into Pi |
| **74HC14** | Schmitt trigger inverter | Cleaning up noisy clock signals |
| **TXB0108** | Auto bidirectional translator | Low-speed control lines (not ideal for fast bus) |

### 2.3 Python Monitoring Example

```python
import RPi.GPIO as GPIO, time

BA_PIN = 17  # GPIO17 wired to VIC-II BA signal via level shifter
GPIO.setmode(GPIO.BCM)
GPIO.setup(BA_PIN, GPIO.IN)

last_state = GPIO.input(BA_PIN)
t0 = time.time()

while time.time() - t0 < 0.1:  # sample for 0.1 s
    state = GPIO.input(BA_PIN)
    if state != last_state:
        ts = time.time() - t0
        print(f"BA changed to {state} at t={ts*1e6:.1f} us")
        last_state = state
```

**Timing Limitations:** Python's timing is not highly precise — under Linux, this loop might only resolve changes to a few microseconds accuracy and could miss very fast events. For better results, use `pigpio`, which samples GPIOs via DMA in the background with timestamp resolution down to **1 µs or better**.

**Verification:** The VIC-II performs memory accesses at up to ~2 MHz (each access ~500 ns apart during active video DMA), which is challenging to capture perfectly on a Raspberry Pi running Linux. Pigpio can sample a GPIO at up to **1 MHz by default** (1 µs intervals), which may be just enough to catch each cycle.

## 3. Real-Time Interfacing and Co-Processing with the VIC-II

Going beyond observation, one can attempt **real-time interfacing**, where the Raspberry Pi actively interacts with or takes over some functions of the VIC-II.

### 3.1 The 500-Nanosecond Window

**Verification (RasPIC64):** "The communication needs to happen within a time window of approx. **500 nanoseconds**. This includes reading the GPIOs, switching multiplexers and reading again, possibly figuring out which data to put on the bus, doing so -- and getting hands off again on time."

**Verification (Lemon64 forum):** The data bus needs to be stable **100 ns before PHI2 falls** (T_DSU), and remain stable until **10 ns after PHI2 has fallen** (T_HR). Minimum is **50 ns from the falling edge of phi2**.

### 3.2 Real-Time Interfacing Projects

| Project | Description | Status |
|---------|-------------|--------|
| **C64–Pi Interface** (Kim Jorgensen) | Uses Raspberry Pi with modified Frodo emulator; SMI/DMA for bus sampling | Historical |
| **RasPIC64** | Bidirectional communication framework for Pi 3B/3B+ | **Superseded by Sidekick64** |
| **Sidekick64** | Versatile software-defined cartridge for C64/C128 | Active |
| **SIDKick Pico** | RP2040/RP235x dual-SID/FM replacement | Active |

**Verification (RasPIC64 README):** "This project has been superseded by Sidekick64. Please follow this link, you'll find an update of RasPiC64 there."

**Verification (RasPIC64):** The project uses a **Fast Interrupt Handler (FIQ)** which handles GPIO reading, preloading caches if required, and reacts properly. The timing is done using the ARM's instruction counters. Circle (bare-metal C++ library) provides the foundation.

## 4. Electrical Considerations: Voltage Levels and Buffers

### 4.1 Core Constraint

The C64 uses **TTL 5-volt logic**, while the Raspberry Pi's GPIO operates at **3.3V CMOS levels**. Directly connecting a 5V output to a Pi's GPIO will damage the Pi. Conversely, a 3.3V output from the Pi might not be recognized as a valid logic "1" by a 5V TTL input in some cases.

### 4.2 Level Shifting Solutions

| Component | Type | Use Case | Notes |
|-----------|------|----------|-------|
| **74HC4050** | Hex buffer (unidirectional) | Shifting 5V down to 3.3V | Vcc=3.3V, 5V-tolerant inputs |
| **74HCT245 / 74LVC245** | 8-bit bus transceiver | Bidirectional data bus | Direction pin selects read/drive |
| **TXB0108** | Auto bidirectional translator | Low-speed control lines | Drive strength low; not for C64 bus |
| **Resistor divider** | Passive level reduce | One-way 5V to 3.3V | May distort fast edges |
| **Open-collector + pull-up** | Transistor/MOSFET network | Open-drain signals | Not for bidirectional bus |

**Verification:** RasPIC64 uses "level shifters and multiplexers" because "the number of GPIOs of a standard RPi 3B/3B+ is too low to simply connect all signals to GPIOs." The wiring diagram is available in `RasPIC64_Circuit.jpg`.

### 4.3 Signal Integrity

Long wires between a Pi and a C64 can pick up noise or introduce ringing. Best practices include:
- Keep wiring short
- Use ribbon cables or twisted pairs for important lines
- Add series resistors (~100 Ω) on fast lines to dampen ringing
- Use decoupling capacitors (0.1 µF) near each buffer IC
- Use Schmitt-trigger buffers (74HC14) on clock/interrupt lines

## 5. Wiring Diagrams and Configurations

### 5.1 Generic Wiring Setup

```
C64 (VIC-II/CPU bus)          Interface                    Raspberry Pi GPIO
====================          =========                    ==================
D0 ---+                       +--< Level shift (bi-dir) >-- GPIO2
      |---< 74LVC245 (Dir=R/W) >---+--< Level shift (bi-dir) >-- GPIO3
D1 ---+                       ...                            ... GPIO4
...                           +--< Level shift (bi-dir) >-- GPIO... (D7)
D7 ---+
A0 --------< 74HC541 (5V->3.3V buffer) >------- GPIO...
A13 -------< 74HC541 (5V->3.3V buffer) >------- GPIO...
Φ2 --------< 74HC14 Schmitt trigger >--------- GPIO... (optional)
R/W -------< 74HC4050 buffer >---------------- GPIO...
BA --------< 74HC4050 buffer >---------------- GPIO...
AEC -------< 74HC4050 buffer >---------------- GPIO...
IRQ -------< 74HC4050 buffer >---------------- GPIO...
RESET <----< MOSFET level shift >------------> GPIO... (Pi can drive Reset low)
```

### 5.2 Specific Configuration: Expansion Port Cartridge

The Commodore 64's expansion port is a 44-pin edge connector exposing address bus (A0–A15), data bus (D0–D7), Φ2, BA, φ0 (dot clock), IRQ, NMI, RESET, ROM select lines (/ROML, /ROMH, /IO1, /IO2), and power.

**Verification (RasPIC64):** "For the aforementioned use cases where we need to read address lines A0-A12, IO1, IO2, ROML, ROMH, Phi2, Reset, SID-chipselect, R/W and read/write data lines D0-D7 (plus GPIOs for controlling the circuitry). This makes the use of level shifters and multiplexers necessary."

**Verification (Sidekick64):** "Sidekick64 is a result, or cumulation, of the RasPIC64 project, which is the framework enabling a RPi to bidirectionally communicate on the bus of a Commodore 64/128."

## 6. Software Implementation and Examples

### 6.1 Python GPIO Access (Basic Monitoring)

```python
import RPi.GPIO as GPIO
IRQ_PIN = 25  # connected to /IRQ via level shifter (active low)

GPIO.setmode(GPIO.BCM)
GPIO.setup(IRQ_PIN, GPIO.IN, pull_up_down=GPIO.PUD_OFF)

def on_raster_interrupt(channel):
    print("Raster Interrupt at:", time.time())

GPIO.add_event_detect(IRQ_PIN, GPIO.FALLING, callback=on_raster_interrupt)
```

### 6.2 High-Performance Access

| Technique | Description | Timing |
|-----------|-------------|--------|
| **C + mmap** | Direct GPIO register access via /dev/mem | Tens of ns |
| **DMA via SMI** | Secondary Memory Interface for high-speed parallel data | µs-level streaming |
| **Bare Metal (Circle)** | No OS; FIQ for cycle-exact response | <500 ns |
| **FPGA Hybrid** | CPLD for sub-500ns sync + Pi for computation | Deterministic |

**Verification (RasPIC64):** "I implemented the communication in a fast interrupt handler (FIQ) which handles GPIO reading, preloading caches if required, and reacts properly. The timing is done using the ARM's instruction counters. I use Circle for bare metal programming the RPi."

**Verification:** "Unfortunately other features which require IRQs (e.g. USB) interfere with the FIQ and do not work."

## 7. Challenges in Timing, Signal Integrity, and Bus Contention

### 7.1 Signal Timing

The VIC-II and CPU time-share the memory bus on a **500 ns cycle granularity**. For real-time interaction, the Pi must adhere to this schedule precisely. Any delay beyond the allotted window can cause failure.

**Verification (RasPIC64):** "The communication needs to happen within a time window of approx. 500 nanoseconds. ... In this case one has to put the next byte on the bus and if too late, the C64 will most likely crash."

### 7.2 Bus Contention

Bus contention occurs when two devices drive the same bus lines simultaneously. The design must ensure that transceivers are enabled at the correct times. Use signals like R/W and BA/AEC to determine when the Pi should listen versus drive.

### 7.3 Limited GPIO Count

A Raspberry Pi has at most 28 usable GPIO pins. The C64's bus requires over 20 signals. This mismatch means one must either prioritize signals or use external multiplexers.

**Verification (RasPIC64):** The project uses multiplexers to handle more signals than the Pi has pins available, requiring the Pi to toggle multiplexer select lines and read multiple samples to reconstruct full bus state.

## 9. Conclusion

Wiring a Raspberry Pi to a Commodore 64's VIC-II chip is an ambitious undertaking that bridges four decades of computing technology. Key takeaways:

1. **Voltage compatibility is critical** — Raspberry Pi GPIO is 3.3V and not 5V tolerant. Always use level shifters.
2. **Passive monitoring** is achievable with simple wiring and Python scripts, limited by sampling rate.
3. **Real-time interfacing** requires sub-500 ns response times, achievable only with bare-metal programming (FIQ, Circle) or FPGA assistance.
4. **The RasPIC64 framework** (superseded by Sidekick64) demonstrated bidirectional communication with the C64 bus.
5. **Modern replacements** (SIDKick Pico, MiSTer FPGA) provide alternatives for chip emulation without custom hardware.

**LabTech Recommendation:** For passive monitoring, use `pigpio` with level shifters (74HC4050, 74HC541). For active interfacing, use the Sidekick64 framework (successor to RasPIC64) with bare-metal Circle and FIQ. For SID replacement, use SIDKick Pico with RP2040/RP235x.
