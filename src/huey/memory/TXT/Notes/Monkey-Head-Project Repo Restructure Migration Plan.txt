Monkey-Head-Project Repo Restructure Migration
Plan
Executive summary
Enabled connectors (used first): github  (repo: DylanLRPollock/Monkey-Head-Project ).
This report produces a practical, engineer-ready  repository restructuring to-do list that prioritizes: (a)
making  the  Python  runtime  importable  and  CI-green,  (b)  separating  “runtime  code”  from  “platform/
packaging artifacts” and “canon content,” and (c) setting the team up for a controlled  staging → pre-
release (v84.3-pre) → freeze → rewrite cycle already described in the repo’s operating docs. The repo
currently includes a Python package declared as hueyos  with requires-python = ">=3.13,<3.15"
and console scripts, including huey-api = "huey.api:main" . 
 The most urgent structural flaw is
that a large portion of the intended  hueyos  package appears to live under  invalid Python package
directory names (notably  src/ai-os/ ), while tests and runtime modules import  hueyos.* , which
creates avoidable breakage and complicates the upcoming rewrite. 
This plan is  deployable as a migration sequence: it includes a proposed taxonomy, explicit file/folder
actions  (keep/move/rename/rewrite/delete),  sample  git  commands,  CI  updates,  rollback  rules,  and
verification/acceptance criteria.
Assumptions (explicit, per request; no clarifying questions): - Default branch is  main , and restructuring
work is performed via feature branches merged back to main . CI currently runs on main  and develop .
 - Where a file/folder is not discoverable in the sampled listings, it’s labeled UNSPECIFIED (not assumed
absent forever). - Any “exact port”, “credential”, “serial protocol”, “GPIO map”, etc. not present in repo text is
treated as  UNSPECIFIED. - This report lists  high-value, discovered paths and provides a deterministic
script  workflow  to  produce  a  complete  inventory  ( git  ls-files )  before  executing  bulk  git  mv
operations.

Naming rules to enforce in the rewrite branch
Importable python packages: must be valid identifiers (e.g., hueyos , huey_gui ), not
hyphenated directories. This aligns with standard src -layout expectations and prevents accidental
import failures.

isn’t selected (Compose can error or ignore). 
Docker images: use Dockerfile best practices (multi-stage builds, least privilege) for production
images. 
pyproject entry points: console scripts must point to real callables ( [project.scripts]
semantics).

Before any bulk  git mv , run  git ls-files  inventory and store it in a versioned directory (e.g.,
.migration/ ). This is how you satisfy “complete file list” deterministically without relying on manual
enumeration.
# One-time inventory snapshot (run from repo root)
mkdir -p .migration/inventory
git ls-files > .migration/inventory/git-ls-files.main.txt
# Optional: categorize for review
grep '^src/' .migration/inventory/git-ls-files.main.txt > .migration/inventory/
src-files.txt
grep '^platform/' .migration/inventory/git-ls-files.main.txt > .migration/

CI, packaging, and deployment implications
Python packaging and entry points
The project declares console scripts under  [project.scripts] .  
 Under PEP 621, these map to
console_scripts  entry points and must reference a valid importable callable. 
 The repo’s security/
maintenance audit explicitly flags that huey-api = "huey.api:main"  is currently mismatched because
src/huey/api.py  is a compatibility wrapper and does not define main . 
 Therefore, the restructure
must include one of: - implement a real main()  callable in the target module, or - repoint the script to an
existing callable that exists after restructure ( hueyos.api:main , path UNSPECIFIED until created).
Additionally, the repository uses a src  layout (packages under src/ ), which is a recognized packaging
pattern for avoiding accidental imports from the working directory. 
 This strengthens the argument that
src/ai-os/  must be renamed to a valid package directory ( src/hueyos/ ).
Docker and Compose
infra/docker/docker-compose.yml  uses Compose profiles ( worker , extras ) and sets defaults via
an anchor  x-service-defaults .  
 Compose profiles behave such that services without a matching
active profile are ignored unless explicitly targeted. 
 This structure should be preserved, but the build
target must be corrected because the current infra/docker/Dockerfile  installs and runs pygpt-
net , not HueyOS. 
For the rewrite, follow Docker’s published best practices: multi-stage builds, minimizing dependencies in
final image, and using USER  (non-root) where possible. 
Debian/platform packaging
The  platform/  directory already includes boot and packaging artifacts (e.g.,  platform/packaging/
dists/... ).  
 Debian’s  policy  docs  distinguish  the  structure  of  Debian  source  packages  (with  a
debian/  directory controlling builds) from raw binary/package artifacts. 
 In restructure terms: - keep
“distribution artifacts” inside platform/  or archives/ , - prevent those artifacts from being treated as
importable runtime code, CI lint scope, or Python packaging inputs.
Uvicorn/FastAPI runtime settings
The  Makefile  runs  uvicorn  huey.api:app  --host  0.0.0.0  --port  1995 .  
 Uvicorn’s  own
documentation confirms these CLI settings ( --host , --port , --reload , --workers , env controls)
are first-class configuration mechanisms. 
 Any restructure must maintain a stable import path for the
ASGI app target ( module:app ) and avoid breaking the runtime invocation pattern.

Rollback, archival policy, and final verification
Rollback and archival policy per change class
Renames/moves ( git mv ): treat each “batch move” as a single commit with an explicit mapping in
commit message. If a move breaks CI, rollback should be git revert <move-commit>  to restore
exact file paths, not partial manual edits.
Structural rewrites (pyproject/entry points, Docker builds): require a paired rollback artifact:
a tag (e.g., v84.3-pre-freeze-candidate , exact name UNSPECIFIED),
and a preserved copy of old configs in archives/config-snapshots/<date>/...  (path naming
UNSPECIFIED).
Canon and long text archives: never delete outright. Move to archives/  or docs/canon/  and
keep a manifest file (e.g., archives/canon-snapshots/<date>/MANIFEST.txt , UNSPECIFIED
exact path). This matches the repo’s doctrine that resets are “audited forks,” not silent amnesia.

Acceptance criteria
The restructure is successful (for the v84.3-pre / freeze bridge) when all of the following are true:
pyproject.toml  entry points correspond to actual callable targets (PEP 621 requirement for
scripts) and CI can install pip install -e .[dev]  and run lint/tests. 
The canonical HueyOS namespace is importable as hueyos  (matching the declared distribution
name), and the old huey  namespace is either compatible or explicitly documented as transitional. 
Docker Compose builds and runs the HueyOS runtime image (not an unrelated pygpt-net -only
image), while preserving Compose profiles behavior. 
“Platform artifacts” remain clearly partitioned under platform/ / archives/ , consistent with
Debian packaging concepts of keeping packaging/build system structure separate from application
runtime code. 
The migration is reversible via tags + revert commits, and the repo retains continuity-of-record
(archive snapshots rather than deletions), consistent with the repo’s own reset/continuity doctrine.
