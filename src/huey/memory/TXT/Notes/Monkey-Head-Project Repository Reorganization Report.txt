Monkey-Head-Project Repository Reorganization
Report
Executive summary
The repository’s core problem is not just sprawl. It is canon drift plus mixed strata. The public website still
presents Huey as a broad embodied platform with dual displays, constitutional governance, PyGPT-net,
Ollama, custom kernels, and phased embodiment, while the current README.md  frames the active target
as a much narrower Huey Brain V1 running on a Lenovo Legion Go with a deterministic MP3 →
transcription → cognition → structured-log loop. At the same time, the repo still exposes a machine-facing
master plan file at master-plan-v30.2.json , even though the README claims the canonical machine-
facing spec is master-plan-v32.0.json . That means public narrative, repo front door, and machine-
facing canon are not synchronized. 
The second problem is layer collision inside the tree. The repo mixes active Python runtime, legacy
runtime, constitutional texts, media assets, release payloads, installer/boot binaries, vendored overlays,
submodules, and security documentation in ways that blur what is live, what is reference, and what is
archival. The most overloaded example is src/huey/memory/ , which currently acts as a code location, a
canon shelf, an asset vault, and an archive bucket at once. The repo also carries substantial binary and
release payload surface, including initrd.gz , kernel images, .deb  packages, .udeb  pools, videos,
and zip archives; GitHub recommends keeping repos small, warns on files above 50 MiB, blocks files above
100 MiB, and explicitly recommends Git LFS or Releases for large binaries. 
The best reorganization is therefore layer-first, not technology-first. I recommend a top-level structure
that separates: canon/  for authoritative present-tense truth, src/  and infra/  for implementation, 
experiments/  for non-canonical lab work, history/  for frozen lineage and payload archives, docs/
for explanatory and operational documentation, assets/  for static media, and third_party/  for
submodules and overlays. This keeps lineage intact because the migration should use git mv  rather
than copy/delete, baseline tags before restructuring, pointer READMEs where old paths vanish, and
release/tag mapping for external references. Git’s own documentation confirms that git mv  updates the
index and, for submodules, also updates .gitmodules  path metadata. 
I recommend doing this in two phases. Phase one should separate canon, history, docs, assets, third-party,
and large artifacts without changing package names or runtime imports. Phase two should tackle the
harder namespace cleanup ( huey  versus hueyos ) only after the tree is structurally clean and the test
baseline is stabilized. That sequencing matters because the current package/test surface already relies on
import shims and mixed namespaces, and the repo’s own recent security remediation summary notes that 
pytest -q  is not currently green in the tested environment due to collection/import issues.

What the repository is signaling now
The live materials currently point in different directions. The website says the public “start here” source of
truth is GitHub and describes a broad, embodied HueyOS stack with phased embodiment and constitutional
autonomy. The README, by contrast, says the active direction is Huey Brain V1 on a Legion Go, with Body,
HIMS runtime, PyGPT-net, and distributed compute explicitly deferred. The machine-facing plan visible in
the repo is still master-plan-v30.2.json , whose content is older than the README’s claimed v32.0
canon. That is the strongest evidence that any reorganization must start by separating historical, 
canonical, and implementation materials before doing anything else. 
The active implementation surface is real, but it is mixed with legacy and doctrinal layers. The repo has a
Python package defined in pyproject.toml  as hueyos  with Python >=3.13,<3.15 , a FastAPI-facing
runtime surface, a CLI entrypoint, large optional dependency groups, and active CI/test/security workflows.
But the tests also reveal import-path accommodation between huey , huey.memory.PY , and src ,
which is a sign that the runtime boundary is not yet cleanly isolated. The security remediation summary
further states that the broader suite currently fails collection in the tested environment, which reinforces
the need to separate structural cleanup from namespace refactoring. 
The tree also includes prior restructuring work products that are useful evidence. docs/unsorted/
repository-restructure-recommendation.md  already proposes separating source, generated
artifacts, release payloads, and ownership boundaries. docs/unsorted/repository-restructure-
inventory.md  already lists concrete moves such as pushing boot/install artifacts under platform/  and
releases under archives/ , consolidating PyGPT integrations, and resolving src/huey  versus src/
hueyos . Those documents are directionally correct, but they remain explanatory documents rather than an
enforced canonical structure. 
Verified audit of high-signal files and path families
The available live connectors did not expose a lossless recursive tree API with exact size and last-modified
metadata for every tracked file. The repository itself does contain a generated git ls-files  inventory
and a recent artifact-surface report, which together make the overall content families clear, but not every
long-tail per-file date could be confirmed interactively. Where exact values were not retrievable from live
metadata, I mark them as unspecified rather than guessing.

Proposed layered target structure
The least-destructive structure is one that preserves the familiar root operational surfaces ( src/ , 
tests/ , .github/ , infra/ ) while moving canon, history, experiments, and third-party into
unmistakable top-level layers.

Migration plan and lineage preservation
The migration should preserve history through small-batch git mv  commits, not a single mega-rename.
Git documents that git mv  updates the index and stages the rename; it also updates .gitmodules
path information when moving a submodule. GitHub Releases are the right place for deployable binaries
attached to a tagged point in history.

Open questions and limitations
A few details remain explicitly unspecified in the accessible evidence and should be treated as options, not
facts:
Exact full per-file appendix: I verified the repo’s structure, major families, and many exact files, but
I could not retrieve a fully lossless live recursive tree with exact size and last-modified metadata for
every path through the exposed connector interfaces. The repo’s own generated inventory and
artifact report make the high-level structure clear, but a local scripted export is still the right way to
produce the final CSV-grade appendix. 
Preferred Python import namespace: huey  versus hueyos  should be resolved in phase two,
after structure cleanup, because the current tree shows both names in live use. 
Whether offline installer pools are first-class product goals: if yes, some .udeb /boot payloads
may remain in Git or LFS; if not, they should move to Releases/object storage. 
LFS entitlement and bandwidth plan: GitHub LFS limits depend on account plan; if that is not yet
decided, prefer Releases for larger public payloads and reserve LFS for assets that genuinely need
checkout-time fetch semantics.
