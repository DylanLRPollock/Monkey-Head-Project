**Historical Context:** Llama 2 was released in July 2023 with a permissive commercial license, establishing itself as the default foundation for hundreds of community fine-tuning projects. As of early 2026, Llama 2 weights remain freely downloadable, but the Llama 3 and Llama 4 families offer substantially better performance across all benchmarks, and most active users have migrated.

**Mistral 7B v0.3 Performance (2026 Benchmarks):**

| Metric | Value |
|--------|-------|
| **Decode Speed** | 56.4 tok/s |
| **VRAM Used** | 6,722 MiB |
| **Quality Score** | 5/6 (best among tested models) |
| **Context Scaling** | 53% speed reduction at 32K vs baseline |

**Key Insight:** Mistral 7B uses a dense transformer with Grouped-Query Attention (GQA) and sliding window attention. All 7.3B parameters are active on every token, with no MoE or PLE.

### 1.2 Translation Models

**NLLB-200 (No Language Left Behind):**
- Meta's open-source translation model supporting **200+ languages**
- Available in distilled 600M parameter version
- Can run fully offline via HuggingFace Transformers or browser deployment

**Practical Deployment:** NLLB-200 distilled 600M is "light enough for a free CPU host" and runs fully offline.

## 2. Setup in a Multi-GPU Environment

### 2.1 Environment Preparation

**Required Libraries:**
```bash
pip install transformers accelerate deepspeed bitsandbytes
pip install torch --index-url https://download.pytorch.org/whl/cu121
```

**CUDA Configuration:**
```bash
export CUDA_VISIBLE_DEVICES=0,1,2,3
```

### 2.2 Model Loading with HuggingFace Accelerate

**Simple Multi-GPU Loading:**
```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_name = "meta-llama/Llama-3.1-70B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    device_map="auto",           # Automatic multi-GPU distribution
    torch_dtype=torch.float16,   # Half precision
    load_in_8bit=True            # Optional: 8-bit quantization
)
```

**How `device_map="auto"` Works:**
- Automatically fills all available GPU memory first
- Then uses CPU RAM for overflow
- Finally uses disk (slowest option) if needed
- **Limitation:** Only one GPU is active at any given moment; GPUs wait for the previous GPU to send output

### 2.3 DeepSpeed ZeRO-Inference

**For More Efficient Multi-GPU Inference:**
```python
import deepspeed

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16
)

ds_engine = deepspeed.init_inference(
    model,
    dtype=torch.float16,
    tensor_parallel_degree=4,    # Use 4 GPUs
    mp_size=4
)
model = ds_engine.module
```

**How ZeRO-Inference Works:**
- Partitions a massive model across multiple GPUs
- Each GPU only activates and loads the layers it needs
- **Drastically reduces per-GPU memory during inference**

### 2.4 Memory Format Options

| Format | Memory Reduction | Accuracy Impact | Use Case |
|--------|-----------------|-----------------|----------|
| **FP16/BF16** | 50% vs FP32 | Minimal | Default choice |
| **8-bit (bitsandbytes)** | ~75% vs FP32 | Low | Larger models |
| **4-bit (GPTQ/GGUF)** | ~87% vs FP32 | Moderate | Maximum efficiency |

## 3. Multi-GPU Resource Management

### 3.1 CPU vs GPU Allocation

| Task | Recommended Device | Rationale |
|------|-------------------|-----------|
| **Neural inference** | GPU | Matrix operations are GPU-optimized |
| **Tokenization** | CPU | Fast, parallelizable, CPU-bound |
| **Orchestration logic** | CPU | PyGPT-net agent logic |
| **Text pre/post-processing** | CPU | Lightweight operations |

### 3.2 Memory Management

**Accelerate's Layer Streaming:**
- Weights are streamed from CPU → GPU → CPU on the fly
- Each time an input passes through a layer, it's sent from CPU to GPU
- The output is calculated, and the layer is removed from GPU

**Optimization Tips:**
- Use `no_split_module_classes` to keep certain modules together
- Pin frequently used layers to GPU
- Use memory-mapped weights for faster loading

### 3.3 Batching and Parallel Streams

| Strategy | Description | Trade-off |
|----------|-------------|-----------|
| **Model Parallel** | One model across all GPUs | Lower latency per request |
| **Data Parallel** | One model per GPU | Higher throughput for many requests |
| **Hybrid** | Combine both | Complex but optimal |

## 5. Security and Privacy Considerations

### 5.1 Data Privacy

- **Offline inference:** No data leaves the machine
- **GDPR compliance:** Local processing keeps data residency internal
- **Sensitive data:** Camera feeds, conversations, sensor data stay within controlled environment

### 5.2 System Security

| Threat | Mitigation |
|--------|------------|
| **Unauthorized access** | OS updates, firewall, authentication |
| **Insider threats** | Sandboxing, access control |
| **Prompt injection** | Output filtering, constitutional AI |
| **Model tampering** | Checksums, verified sources |

### 5.3 Model Content and Behavior

**Mitigation Strategies:**
- **System prompts:** Steer model away from unsafe instructions
- **Output filtering:** Moderation models or heuristics
- **Isolation:** Model should not have system privileges
- **Validation:** Treat model output as untrusted

## 6. Trade-offs: Open-Source vs API

| Factor | Open-Source Local | OpenAI API |
|--------|-------------------|------------|
| **Accuracy** | Good (approaching GPT-4 on some tasks) | Best available |
| **Latency** | No network delay; dependent on local hardware | Network-dependent |
| **Cost** | Fixed hardware cost | Variable per-token cost |
| **Privacy** | Complete data sovereignty | Data leaves premises |
| **Control** | Full customization | Limited by policy |
| **Maintenance** | Manual updates | Automatic improvements |

**Verification (Privacy Value):** "For any team handling customer data, medical records, legal documents, or proprietary source code, sending that data to a third-party API endpoint creates a compliance surface area... Local inference eliminates the most uncomfortable question in any data protection impact assessment: 'Where does the data go?' When the model runs on hardware you control, the answer is nowhere."

## 7. Integration into Monkey Head Project Structure

### 7.1 Integration Patterns

| Pattern | Description | Use Case |
|---------|-------------|----------|
| **Service Mode** | Ollama/vLLM runs as separate service | Simpler integration; managed GPU usage |
| **Embedded Mode** | Model loaded in HueyOS process | Lower overhead; higher memory usage |

### 7.2 Ollama Integration (Recommended)

**Setup:**
```bash
# Install Ollama
curl -fsSL https://ollama.com/install.sh | sh

# Pull model
ollama pull llama3.1:70b

# Start server
ollama serve
```

**API Access:**
```bash
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.1:70b",
  "prompt": "Why is the sky blue?",
  "stream": false
}'
```

**Verification:** "Ollama runs locally. We don't see your prompts or data when you run locally."

### 7.3 Embedded Mode

```python
# In initialization
if config.LLM_PROVIDER == "local":
    model_name = "meta-llama/Llama-3.1-70B-Instruct"
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModelForCausalLM.from_pretrained(
        model_name,
        device_map="auto",
        torch_dtype=torch.float16
    )

# In request handler
if config.LLM_PROVIDER == "local":
    input_ids = tokenizer.encode(user_query, return_tensors='pt').to(model.device)
    output = model.generate(input_ids, max_new_tokens=256)
    reply = tokenizer.decode(output[0], skip_special_tokens=True)
```
