Windows Longhorn Client Preview 2 Build 6.0.4074
AMD64
A technical, research-driven assessment for Huey‑VistaBox: provenance, NT 6.0 x64 behavior, virtualization, and
PuTTY 0.83 compatibility
Executive summary
Windows Longhorn build 6.0.4074.idx02.040425-1535 (“Longhorn Client Preview 2”) is the second and
last widely distributed pre-reset Longhorn preview, provided to attendees at WinHEC 2004 (Seattle,
May 4–7, 2004) as a developer-facing preview for hardware/driver ecosystem preparation. 
 This build is
historically “famous” because it is one of the clearest externally available snapshots of the pre-reset
Longhorn vision—especially its composited desktop experiments and early “Aero” lineage—but those
headline UI characteristics are primarily true of the x86 build rather than AMD64. 
For AMD64 specifically, BetaWiki’s evidence-based cataloging reports that managed/.NET-adjacent UI
features do not function (explicitly including the Sidebar, MIL effects, and Aurora), which is a major
constraint if your goal is “the most Vista-like Longhorn.” 
 The AMD64 4074 build can still be valuable as a
“minimum viable NT 6.0 x64” environment, but you should treat it as a kernel + Win32 compatibility
testbed more than an authentic “Aero demo box.”
For your stated must-have—PuTTY 0.83—the evidence is encouraging but not absolute. PuTTY 0.83
(released 2025‑02‑08) explicitly restored Windows XP compatibility after 0.82 temporarily broke it, and
PuTTY’s own FAQ notes that 0.83 still runs on Windows XP even though 0.82 did not. 
 Since XP predates
NT 6.0, this strongly suggests PuTTY 0.83 is conservative in its Win32 dependencies and should in principle
run on Longhorn 4074—especially if you use the standalone EXE instead of the MSI, because Longhorn-
era Windows Installer compatibility is repeatedly a pain point in vintage/pre-release Windows stacks. 
Operationally, your main technical risks in 4074 AMD64 for Huey‑VistaBox are network reliability and
logon-critical services: BetaWiki documents DNS failures when DNS is obtained via DHCP, and also
warns that Terminal Services and the User Profile Service are required for successful logon
(misconfiguring them can yield hangs/black screens or broken profiles). 
 These risks are manageable
with a disciplined VM configuration and a reproducible “stabilization checklist.”
Finally, from a security and lab governance standpoint: you should treat pre-release Longhorn as 
structurally unpatchable and unsafe for real data. CISA’s general guidance on end-of-support Windows
emphasizes that unsupported systems stop receiving security updates and become higher risk for
compromise. 
 Your own HueyOS program framing also emphasizes offline-first operation and careful
security/data handling in principle, which aligns with running Longhorn only in isolated test roles.

Introduction
Longhorn (the codename that ultimately became Windows Vista) is best understood as two projects
separated by a substantial reset. The early (“pre-reset”) branch attempted to deliver a set of “pillars” that
Microsoft publicly described in 2003 as:
Avalon (new presentation/graphics subsystem),
WinFS (new storage subsystem),
Indigo (new communications/Web-services subsystem). 
At WinHEC 2004, Microsoft positioned Longhorn preview code as a practical on-ramp for OEMs and IHVs—
especially to begin work on native Longhorn device drivers and to support forward-looking graphics/
driver architectures. 
 Build 4074 is the canonical artifact of that moment: it is explicitly described as the
WinHEC 2004 “Preview 2” build distributed at the conference. 
By August 2004, Microsoft publicly acknowledged schedule and scope changes (including shipping WinFS
later) while targeting broad availability in 2006, reflecting the broader reset dynamics. 
 That reset
matters for you because:
4074 is pre-reset: it captures ambitious UI experiments but is also inherently incomplete and
unstable.
Later Vista-era builds (e.g., 5048, 5112, 5384.4) are post-reset and typically more “Vista-like” in day-to-
day operation, especially on AMD64. 
In your Huey‑VistaBox context, HueyOS is described as an offline-first OS/software layer coordinating
local AI, tools, and hardware—currently grounded in a real Linux-first baseline. 
 That architecture
strongly suggests a Windows Longhorn guest should be treated as a contained compatibility island (e.g.,
legacy UI/driver research, “minimum x64 Windows” demonstrations, or controlled client tooling), not as a
trusted operational node.
Methods of research
This assessment uses a “primary-first, triangulated secondary” method.
First, your connected GitHub repository was reviewed to anchor assumptions about HueyOS and the
intended lab posture (offline-first orientation, security/data-handling emphasis, and practical OS
minimization). 
 A supporting internal note on OS “debloating” was also reviewed to align stabilization
recommendations with your project’s general preference for lean systems. 
Second, build metadata and behavioral specifics were drawn from high-signal Longhorn archival
compendia (notably BetaWiki and the BetaArchive Wiki) that catalogue build strings, compile dates, and
known defects with unusually granular detail. 
Third, Microsoft primary sources were used to validate historical context (WinHEC 2004 positioning and
Longhorn “pillars”) and to ground subsystem explanations (DWM and WOW64 behavior) in official technical
descriptions.

NT 6.0 x64 mechanics that matter for “minimum viable Windows”
Even if you ignore the “Vista-like” UI layer, the AMD64 build is still a real NT-family 64-bit OS and inherits the
fundamental constraints of x64 Windows that directly affect testbed compatibility.
WOW64 is the standard 32-bit compatibility subsystem on 64-bit Windows, supporting 32-bit GUI/
console/service apps while isolating 32/64-bit DLL worlds and preventing bitness mixing within a
single process. 
WOW64 uses file system redirection (e.g., redirects many 32-bit accesses targeting %windir%
\System32  to %windir%\SysWOW64 ) to prevent 32-bit processes from loading 64-bit system
binaries. 
64-bit Windows does not support 16-bit Windows applications, and it does not support 32-bit
kernel-mode drivers. 
For Huey‑VistaBox, this implies:
A “modern-ish” 32-bit userland artifact like PuTTY 0.83 is conceptually compatible if WOW64 is present
and stable.

Known defects and reliability issues relevant to your use case
Build 4074’s known issues are extensive, but the following are the ones most tightly coupled to a PuTTY-
centric VM role:
DHCP-acquired DNS can break name resolution, and the recommended mitigation is to configure
DNS manually. 
The OS depends on Terminal Services and the User Profile Service for logon; disabling or mis-
setting these services can yield black-screen hangs or broken profiles/Explorer initialization failures. 
There are reports of severe hangs shortly after logon in some multi-core configurations,
suggesting you should treat CPU-core count as a stability lever (start low, scale up only if stable). 
Internet Explorer’s built-in download manager is reported broken, with downloads not working
at all in some cases—meaning you should not rely on in-guest web retrieval for PuTTY or drivers. 
Setup/WinPE has input pitfalls: PS/2 mouse driver is broken in the Preinstallation Environment,
which directly affects VM installs because many virtual pointing devices present as PS/2 by default. 
The build contains an evaluation timebomb (~180 days from installation) that forces logoff/blocks
use after expiration. 
Virtualization behavior and recommended VM configuration
BetaWiki’s VM guide provides two kinds of virtualization guidance: (a) hypervisor-wide caveats for vintage
Windows, and (b) configuration templates for specific Windows eras/build families.
Key caveats to take seriously:
Older Windows builds may run better on older VMware compatibility modes, and later host/
hypervisor behaviors can break DWM or cause instability. 
VMware Easy Install can mis-detect AMD64 Longhorn builds as x86 XP and attempt to inject wrong
drivers, producing setup errors. 
DWM can be fragile in virtualization, including black screens or crashes on some host systems. 
A pragmatic baseline for Milestone 7 pre-reset Longhorn x64 (the family containing 4074) in VMware is:
1 VM, ~1.5 GB RAM, 1 CPU / 2 cores, IDE disk (~25 GB), USB 2.0, video memory ~128 MB, 3D
acceleration enabled, OS type set to “Windows XP Professional x64 Edition,” hardware compatibility
Workstation 6.5–7.x. 
For sound and accelerated graphics features, the guidance emphasizes VMware 6.5.2 driver
packages extracted from VMware guest additions, rather than modern VMware Tools.

may not be compatible, but extracted driver packages often are, and it provides VMX-level tweaks to

PuTTY 0.83 compatibility assessment for Longhorn 4074 AMD64
From PuTTY’s official release materials:
PuTTY 0.83 is the latest release as of its release page, dated 2025‑02‑08, and offers both MSI
installers and standalone executables (including a direct putty.exe  download). 
PuTTY’s official changelog states: “Windows XP support was accidentally broken, and now
reinstated.”
PuTTY’s wishlist bug record details how 0.82 binaries failed on XP due to a manifest-related issue and
that this was fixed in 0.83. 
The PuTTY FAQ clarifies that the project targets currently supported Windows, but older versions
may still work; explicitly: “PuTTY 0.83 still runs on Windows XP – but the previous release 0.82
didn’t.”
Inference (clearly labeled): If PuTTY 0.83 is engineered to remain compatible with Windows XP-era
constraints, then it is likely to operate on Longhorn 4074’s Win32 surface area as well—particularly as a
standalone EXE—because Longhorn 4074 is still a classic Win32 desktop and (as an NT-family successor-era
build) should not be less capable than XP in baseline user-mode APIs. This inference is supported indirectly
by PuTTY’s XP-compatibility posture and by Microsoft’s general compatibility framing of WOW64 on x64
Windows. 
The practical risk is less “does PuTTY run?” and more “does networking behave?” because DNS/DHCP issues
are specifically documented in 4074. 
Discussion
Is 4074 AMD64 the best “polished / Vista-like Longhorn”?
As an expert-to-expert judgment grounded in the cited evidence: no—at least not on AMD64.
Build 4074 x86 is the variant most associated with “complete” pre-reset MIL/DWM visual experiments. 
But the AMD64 build is explicitly documented as missing/breaking core managed UI features (Sidebar/MIL/
Aurora), which are central to that “Vista-like Longhorn” identity. 
If your actual goal is “minimum 64-bit Windows OS that can run PuTTY”, 4074 AMD64 can still be
defensible because:
It is a real NT 6.0 x64 environment (useful architecturally as a boundary case),
It has a strong historical pedigree and well-documented quirks,
You can design Huey‑VistaBox around PuTTY + a small controlled toolset, not around Longhorn
eye-candy.

Virtualization guidance for Huey‑VistaBox
Given Huey‑VistaBox’s likely role (a demonstrative/compatibility VM), prioritize: reproducibility, deterministic
networking, and “portable apps first.”
Prefer VMware over VirtualBox if you care about any DWM experiments, but expect fragility
regardless; BetaWiki explicitly warns that DWM may render artifacts, black screens, or crashes
depending on host hardware and VM settings. 
Use older compatibility modes (Workstation 6.5–7.x hardware compatibility in VMware terms)
where possible; multiple sources and community practice indicate setup/driver behavior can fail if
you present too modern a virtual hardware profile. 
Treat extracted driver packages as the first-line path, not modern “Tools,” consistent with
longhorn.ms’s note that Tools may be incompatible while drivers remain usable. 
Security and forensics: why isolation is not optional
Even though Longhorn 4074 is a research target, it should be treated as high-risk software:
It is not supported and cannot receive modern security updates; CISA’s end-of-support guidance for
Windows makes the general point that unsupported systems no longer receive updates/hotfixes and
become more vulnerable. 
HueyOS’s own framing emphasizes that any system capable of processing/transmitting data carries
risk and that risk increases when network access is enabled—an especially relevant reminder when
running a pre-release Windows VM. 
So: keep Huey‑VistaBox behind NAT or host-only networking, avoid exposing services, and never store
secrets in the guest.

Conclusion
Windows Longhorn 6.0.4074 AMD64 is a historically significant WinHEC 2004 preview build with a well-
mapped defect surface, making it a legitimate candidate for a research VM and a “minimum NT 6.0 x64”
demonstration OS. 
However, it is not the best choice if your primary criterion is “most polished / Vista-like Longhorn,” because
the AMD64 build is explicitly documented as lacking functional Sidebar/MIL/Aurora features that define the
famous 4074 experience. 
For your PuTTY requirement, PuTTY 0.83 is a strategically good target because it intentionally maintains XP
compatibility and offers standalone executables, which is exactly the posture you want when you cannot
trust MSI/installer stacks in a pre-release OS. 
 The primary engineering work in Huey‑VistaBox will likely
be network stabilization (manual DNS, conservative VM NIC choices) and service discipline (do not
disable logon-critical services).

Appendix: reproducible install + stabilization checklist for Huey‑VistaBox (4074 AMD64)
Create VM + snapshot plan
Create VM with conservative virtual hardware (IDE disk, minimal devices).
Disable “easy install” / unattended behaviors that may inject mismatched drivers. 
Define snapshot points: post-install boot, post-network stabilization, post-driver install, post-PuTTY
validation.
Install OS (WinPE ergonomics)
Expect WinPE input friction: PS/2 mouse in WinPE is documented broken; plan to navigate setup with
keyboard or a USB-pointing configuration. 
First boot sanity checks (do not optimize yet)
Confirm you can log on repeatedly without hangs.
Do not disable services during early stabilization.
Logon-critical service checks
Ensure Terminal Services and User Profile Service remain enabled/automatic because the build is
documented as relying on them for correct logon/session initialization. 
Networking: fix DNS before blaming PuTTY
If you can ping by IP but not resolve hostnames, set a manual DNS server rather than DHCP-
provided DNS (explicitly documented as a failure mode). 
Prefer NAT or host-only networking; avoid bridged exposure unless you have a controlled lab VLAN.
