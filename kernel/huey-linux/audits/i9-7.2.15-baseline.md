# i9 workstation pre-build inventory — Linux 7.2.15

**Status:** observed 2026-11-14/15 from an operator-supplied read-only audit.
**Purpose:** technical compatibility checklist for `7.3.4-huey-testing1`.
**Privacy:** excludes filesystem UUIDs, serials, host identifiers and user paths.
**Important:** the complete 11,982-line running kernel `.config` has NOT
been supplied for differential analysis. This is an inventory, not a qualified
7.3.4 configuration or proof of real driver compatibility.

## Observed platform

- Debian Forky, `7.2.15+deb14-amd64`, `PREEMPT_DYNAMIC`.
- Intel Core i9-12900K, 24 logical CPUs, `intel_pstate=active`, microcode
  `0x3e`, 15 GiB host RAM.
- ASUS TUF GAMING Z790-PLUS WIFI, BIOS 1836 (2026-04-16).
- UEFI boot with EFI system partition on a Kingston SATA SSD; Secure Boot
  currently **disabled**.
- Default GCC 16.2.0; `gcc-14` and `g++-14` installed and preferred for
  CUDA 12.9 compatibility. GNU make 4.4.1.
- One NVIDIA Tesla V100 PCIe 32 GiB at PCIe 3.0 **x16** (full width), NVIDIA
  proprietary 580.196.07 bound. DKMS reports installations for 7.2.12 and
  7.2.15. At 0% utilization: 45 C GPU, 43 C memory, ~38.7 W.
- CUDA toolkit `nvcc 12.9.86` and `compute_70` compilation target available.
  `nvidia-smi` showing `CUDA Version 13.0` is a driver API compatibility
  report, **not** evidence that toolkit 13 is installed.
- MSI RX 570 bound to `amdgpu` in chipset-connected PCIe 3.0 **x4** slot.
  AMDGPU currently drives the display.
- **Intel UHD 770 is not enumerated in current `lspci` output** (no Intel
  display controller at the usual `00:02.0`). Do not remove the RX 570
  or disable AMDGPU until firmware, motherboard HDMI/DP, i915, Wayland and
  cold-boot fallback have been validated.
- Intel I226-V Ethernet uses `igc`; 700-series Intel Wi-Fi uses `iwlwifi`;
  SATA uses `ahci`.

## Critical storage / boot chain

1. Four Intel Optane M10 NVMe modules (~13.4 GiB each as exposed) are visible
   behind an Intel VMD controller (`vmd` bound). Linux software MD RAID10
   forms `/dev/md0` (~26.8 GiB), containing a **Btrfs root subvolume
   `@rootfs`**. Boot requires VMD, PCIe, NVMe, md_mod/raid10,
   Btrfs, initramfs MD assembly metadata/config and the correct GRUB
   `rootflags=subvol=@rootfs`; preserve all modules and sequencing.
2. Two Kingston SATA SSDs (~223.6 GiB each) have `md2` RAID0 (~443.1 GiB),
   Btrfs-mounted at `/home`. **No redundancy**, high-value data must have
   an external backup before kernel qualification.
3. The same SSDs provide `md1` RAID1 swap (~953 MiB).
4. EFI system partition is `/dev/sdc1` FAT/vfat; its bootloader/fallback
   path is not mirrored automatically by the MD arrays. Preserve and back up
   the EFI contents and GRUB configuration.
5. Two WD 10 TB-class SATA drives form a Btrfs RAID1 at `/10TB` (data,
   metadata and system RAID1). Privileged `btrfs filesystem usage -T`
   reports **no missing capacity** and `btrfs device stats` reports **zero**
   read/write/flush/corruption/generation errors on both drives.
   Unprivileged `btrfs filesystem show` printed `MISSING` because device
   nodes could not be opened; this is **not evidence of failed disks**.
6. **Per-device raw Btrfs scrub counters confirm that no data was scanned:**
   each WD drive reports `data_extents_scrubbed=0`,
   `data_bytes_scrubbed=0`, `tree_extents_scrubbed=10`,
   `tree_bytes_scrubbed=163840`, despite `Status: finished`.
   This is **NOT** a full-data scrub or verified validation of 900 GiB.
   Reported device I/O errors are zero, but no full surface-data validation
   has occurred. Arrange a real full scrub separately, after backup and
   subject to operator approval; a normal writable RAID1 scrub may repair
   bad replicas and is not a strictly read-only operation.

## Baseline kernel configuration observed

- `CONFIG_LOCALVERSION=""`; `CONFIG_LOCALVERSION_AUTO=n`; Debian running
  release nevertheless includes `+deb14-amd64` from distro release
  machinery. Exact `KERNELRELEASE` enforcement remains necessary.
- `CONFIG_VMD=m`, `CONFIG_NVME_CORE=m`, `CONFIG_BLK_DEV_NVME=m`,
  `CONFIG_SATA_AHCI=m`, `CONFIG_BLK_DEV_MD=m`, `CONFIG_BTRFS_FS=m`,
  `CONFIG_EXT4_FS=m`, `CONFIG_MODULES=y`, `CONFIG_MODULE_SIG=y`.
- `CONFIG_DRM_I915=m`, `CONFIG_DRM_AMDGPU=m`,
  `CONFIG_DRM_NOUVEAU=m`. Currently `amdgpu` is bound to the RX 570 and
  `nvidia`, `nvidia_uvm`, `nvidia_modeset`, `nvidia_drm` are loaded.
- `CONFIG_INTEL_IOMMU=y`, `CONFIG_IGC=m`, `CONFIG_IWLWIFI=m`,
  `CONFIG_X86_INTEL_PSTATE=y`, `CONFIG_INTEL_IDLE=y`.
- Additional privileged checks confirm `CONFIG_MD_RAID10=m`,
  `CONFIG_MD_RAID0=m` and **`CONFIG_MODVERSIONS=n`**.
  `sudo modinfo -F version nvidia` reports `580.196.07`;
  `vermagic` is exactly `7.2.15+deb14-amd64 SMP preempt mod_unload`
  (no `modversions` suffix). The V100 driver is operational with module
  versioning disabled. HueyOS now preserves `CONFIG_MODVERSIONS=n` in its
  testing1 profile; code validation does not wrongly require the feature.
  If enabled in a later candidate, explicitly rebuild and retest modules.
- Still missing: the complete 11,982-line `current-kernel.config`, including
  early boot crypto/UEFI options and uninspected base configuration. Upload
  it for a full diff, rather than interpreting omitted lines as disabled.
- `CONFIG_MODVERSIONS` is optional for external modules. When enabled it
  adds symbol CRC checks. A complete matching kernel build and
  `Module.symvers` should be available for reliable external module builds.

## Pending gate before compiling Linux 7.3.4

- Receive and review the complete saved `current-kernel.config`; merge into
  official 7.3.4 source via `olddefconfig`, inspect delta.
- Verify exact source digest/signature and pin `source.lock.json`.
- The running 7.2.15 initramfs has been confirmed to include `vmd.ko.xz`,
  `nvme.ko.xz`, `nvme-core.ko.xz`, `raid10.ko.xz`, `btrfs.ko.xz`,
  `etc/mdadm/mdadm.conf`, `scripts/local-block/mdadm`,
  `usr/sbin/mdadm` and Btrfs hooks. Require those components in the new
  7.3.4 initramfs and retain existing 7.2.15 and 7.2.12 boot entries.
- `df` confirms root and `/boot` are the **same** ~27 GiB Btrfs filesystem,
  with ~14 GiB available; `/boot/efi` has ~966 MiB available and is on
  a single Kingston SSD. `/home` has ~123 GiB free but is MD RAID0;
  `/10TB` has ~8.7 TiB free and uses Btrfs RAID1. Do not put large build
  outputs in root; verify free space before staging kernel packages.
- All three `mdadm --detail` arrays are `clean`. `md0` has 4/4 active
  Optane members, `md1` has 2/2 active Kingston swap members, and
  `md2` has 2/2 active Kingston RAID0 members (no redundancy).
  NVIDIA module version and vermagic match the running kernel.
- Verify Intel iGPU firmware enablement and display connection separately,
  leaving RX 570 fallback in place during initial testing.
- Review `/home` backups and EFI backup before touching boot.
- Verify complete NVIDIA 580.196.07 proprietary modules compile for target
  7.3.4 and preserve the working CUDA and opt-in Vulkan backends.
- Real hardware test and stable qualification have NOT occurred.
