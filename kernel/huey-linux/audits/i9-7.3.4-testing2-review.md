### Initramfs tooling blocker discovered during planning

The pre-existing `src/huey/kernel_build/initramfs_builder.py`
describes passing `mkinitramfs -k <kernelrelease>` and injecting
`MODULESDIR=<private-staging>/lib/modules`. Debian's current
`mkinitramfs` documents **`-k` as "keep temporary directory"**,
not a kernel version option, and *unconditionally* sets
`MODULESDIR="/lib/modules/${version}"` internally.
Thus setting `MODULESDIR` in the environment or in a custom
`initramfs.conf` **does not isolate the input module tree** as
claimed. The selected version is positional. Unprivileged runs can
fail or attempt `depmod` for a missing host `/lib/modules/<version>`.

**HARD BLOCK:** Do not invoke the current initramfs builder against
testing2 until the host-independent module-tree strategy has been
implemented, reviewed, and tested on this Forky version. Do not
populate host `/lib/modules` or use `dpkg -i` just to make the
builder work. Collect privileged *read-only* mdadm/EFI evidence
first. Target-initramfs generation, inspection, fallback boot entries
and NVIDIA security qualification are not yet complete.

Debian reference: https://manpages.debian.org/testing/initramfs-tools-core/mkinitramfs.8.en.html
Upstream source: https://salsa.debian.org/kernel-team/initramfs-tools/-/blob/debian/latest/mkinitramfs
